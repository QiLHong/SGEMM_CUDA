# 00：把源码当作可以亲手验证的教材

> 本页是中文分支新增的学习导读，不是原作者博客的逐段翻译。所有文件路径和调用关系对应本仓库基线 `5a7dcc513d951ba764d51bc9d587b3163f3a894d`。

## 先明确我们在算什么

整个项目围绕同一条公式：`C = alpha * A * B + beta * C`。矩阵形状为 `A[M,K]`、`B[K,N]`、`C[M,N]`，主要 kernel 使用 FP32。不同版本首先改变的是数据访问与线程分工，不是让矩阵乘法变成另一个数学问题。

不要从 12 号开始，也不要先要求自己背下所有模板参数。第一目标是能口述一个线程如何计算一个输出，以及它读写了哪些地址。

## 先追一条调用链

最新研究：[公开 CUTLASS 对照与主循环成本审计](16-公开CUTLASS对照与主循环成本审计.md)，包含七轮实测和逐条 LDS 的硬件服务成本，不再仅根据核函数名字推断架构。

```text
DEVICE=0 ./build/sgemm 2
  └─ sgemm.cu：main
       ├─ 读取 kernel_num 和 DEVICE
       ├─ 分配 A/B/C 与 cuBLAS 参考输出
       ├─ 依次选择多个矩阵尺寸
       ├─ 调用 run_kernel(0, ...) 获取参考结果
       └─ 调用 run_kernel(2, ...)
            └─ src/runner.cu：run_sgemm_coalesce
                 ├─ 配置 gridDim 和 blockDim
                 └─ sgemm_global_mem_coalesce<32><<<...>>>
                      └─ src/kernels/2_kernel_global_mem_coalesce.cuh
```

计时也由 `sgemm.cu` 管理。`runner.cu` 的 `run_kernel` 是编号分发入口，`kernels.cuh` 则汇总头文件。不要把“启动 kernel 的 CPU 函数”与“在 GPU 上执行的 `__global__` 函数”混为一谈。

## 每个版本只做一张小笔记

```text
版本：
数学公式 / 输入输出形状：

必须满足的尺寸与对齐条件：

本机结果与正确性检查：

```

最有用的练习不是把注释背一遍，而是临时不看注释，手算几条地址，再对照结果。注释用于帮助验证理解，不应代替源码本身。

## 第一次运行只比较 0、1、2

按根目录 README 构建 Release 后，串行运行：

```bash
DEVICE=0 ./build/sgemm 0
DEVICE=0 ./build/sgemm 1
DEVICE=0 ./build/sgemm 2
```

先看有没有通过对照校验，再比较**同一尺寸、同一张 GPU**上的 GFLOPS。原 README 的 A6000 数据是历史背景，不是你的 3080 必须达到的目标。本分支没有替你运行这些命令。

如果程序报错，先保存命令与输出，检查尺寸前提；不要立刻放宽误差阈值。11/12 号属于最后阅读的进阶实现，运行前先看 [原版限制](03-原版限制与验证.md)。

## 和 vLLM-LiteQ 的联系

这是概念类比，不是两个项目可直接互换的接口：Linear 通常计算 `Y=X*W^T+b`，而这里实现一般的 `C=alpha*A*B+beta*C`。tile、数据复用、内存访问与启动配置的思路可以帮助阅读 Triton Linear，但这里主要是 CUDA C++ / FP32 SGEMM，不是 INT8 权重量化教程，也不是 CUDA Graph 教程。

学到 5 号后，你应该能解释：为什么一个线程多算几个输出，反而可能减少每个结果所需的内存读取。能解释这个，再回看自己的 INT8 Triton backend 会更容易。
