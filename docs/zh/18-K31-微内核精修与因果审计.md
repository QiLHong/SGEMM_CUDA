# K31：微内核精修与因果审计

本轮继续在同一台 RTX 3080 / SM86 / CUDA 12.4 上研究 K30 V2。目标是检验
寄存器生命周期、shared stage 数和 CTA 规模还能否带来稳定收益，并解释剩余差距。
达到 98% strict FP32 cuBLAS 是研究目标，不是预先保证的结论。

## 1. 故事从哪里继续

[K30 实验](17-K30-Mini-SIMT微内核.md)已经在七轮交错测量及独立三轮复测中，
将同轮 cuBLAS 比例从 K10 的约 91% 提升到约 96%。真正值得保留的经验，是
fragment ownership 与双缓冲同步协议共同改变了执行成本；它不等于“stage 越多越快”。
K30 V1 已减少 shared-load wavefront，却比 K10 慢；V2 才把这一结构与一次 barrier
的循环组织结合成吞吐收益。V3/V4 又证明，增加 shared 容量或 CTA 外形不会自动延续收益。

K31 因此保留现有外积、fragment、shared 布局及 epilogue，实现独立研究入口
[`31_kernel_mini_simt_refine.cuh`](../../src/kernels/31_kernel_mini_simt_refine.cuh)。
K10/K30 均继续作为原始对照。本轮把“源码看起来更早加载”“寄存器数字更低”和
“GPU 实际更快”作为三个需要分别验证的命题，不靠一次最高 GFLOPS 宣布成功。

## 2. K30 的完整微内核映射

```text
128×128 CTA，128 threads
  └─ 2×2 warps，每 warp 64×64
       └─ 4×8 lane lattice，M 方向 interleave=2
            ├─ shared A：As[k*132+m]
            ├─ shared B：Bs[k*128+n]
            ├─ 每 lane：A16 × B8 → 128 个 accumulator
            └─ 每 k：6 条 LDS.128 → 128 次 FFMA/thread
```

设 `w=threadIdx.x/32`、`l=threadIdx.x%32`，则：

```text
warpRow = w/2                 warpCol = w%2
laneM = 2*(l/16) + l%2       laneN = (l%16)/2

m(i) = 64*warpRow + 4*laneM + 16*(i/4) + i%4  i=0..15
n(j) = 64*warpCol + 4*laneN + 32*(j/4) + j%4  j=0..7
acc[i*8+j] 对应 C[blockM+m(i), blockN+n(j)]
```

例如 warp 0 的 lane 0 负责 A 行 `0..3,16..19,32..35,48..51` 和
B 列 `0..3,32..35` 的笛卡尔积；lane 1 的 A 行整体加 4、B 不变；
lane 2 的 A 与 lane 0 相同、B 列整体加 4。lane 16 的 A 行为
`8..11,24..27,40..43,56..59`，B 与 lane 0 相同。
完整 32 lanes × 128 outputs 映射保留在
[历史 lane-mapping.csv](../results/k30-20261013/lane-mapping.csv)，
由 [`analyze_k30_mapping.py`](../../scripts/analyze_k30_mapping.py)枚举检查完整覆盖、
无重复与布局边界。本轮沿用映射，不把同一份结果另称为新测量。

128 个 accumulator 跨全部 K 存活，每个输出依次累加递增的 k。
A16/B8 是当前 k 的计算 fragment；global loader 的 A16/B16 则是下一整个 BK tile
搬运时的临时寄存器数据。这两种 fragment 不能混为一谈。K31 的 lifetime 实验主要
改变后一种临时数据与计算的组织，不改变 accumulator 数量或每个 C 的求和顺序。

## 3. −40% shared-load wavefront 究竟来自哪里

K10 与 K30 的 shared 物理方向相同：A 为 `As[k*(BM+4)+m]`，B 为 `Bs[k*BN+n]`。
K10 每线程持有 A8/B16，K30 改为 A16/B8。两者每 k 均读入 24 个 float，
均执行 6 条 `LDS.128` 和 128 次 FFMA/thread；改变的是 lane 的地址重复模式和
每条 shared load 的服务成本。

|每 warp 每 k|K10|K30|
|---|---:|---:|
|A fragment floats/thread|8|16|
|B fragment floats/thread|16|8|
|A LDS.128 数量 × 每条 wavefront|2 × 2|4 × 2|
|B LDS.128 数量 × 每条 wavefront|4 × 4|2 × 2|
|LDS.128 总数|6|6|
|shared-load wavefront 总数|20|12|

准确的成本分解是：A 从 4 waves 增至 8，B 从 16 降至 4，合计降低 40%。
不能写成“A/B 都减少”，也不能把 wavefront 的减少解释为少算乘加或少读了 40%
的逻辑 fragment 元素。

对同一条 float4 shared load，把相同地址记为相同字母：K10 的 A 是
`aaaa bbbb cccc …`，B 是 `abcd abcd …`；K30 的 A 在前半 warp 为
`abab …`、后半为 `cdcd …`，B 为 `aabbccdd …`、后半 warp 重复相同地址组。
这使 K30 两种操作数的宽 load 都落入本机测得的 2-wavefront 广播服务模式。
零 bank conflict 不代表不同 lane 组织具有相同的基础服务成本。

上述数值来自[逐 PC 历史数据](../results/k30-20261013/source/mainloop-lds.csv)，
不是从总 conflict 倒推：K10 `0x930/0x940` 的 A 各为 2 waves，
`0x950/0x960/0x970/0x980` 的 B 各为 4；K30 V2 的全部 96 个 hot LDS 位置
均为 2。4096³ 的 `4096 warps × 4096 K` 因而对应：

```text
动态 LDS：两者都是 100,663,296
K10 主循环 waves：335,544,320
K30 主循环 waves：201,326,592
```

这里的 2 waves 是指定访问模式的实测，不是所有架构、宽度与广播模式的绝对下限。
同样不能把一条 LDS.128 按 `32×16/128` 一律判为 4 waves，忽略广播。
[NVIDIA shared-memory 指标定义](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html#shared-memory)
区分 instruction、request、wavefront 与 bank conflict；本报告遵循这一口径。

## 4. Shared Layout 对照：本轮的停止条件

公开 CUTLASS v3.5.1 的实际 SM80 SIMT multistage 特化，使用 A=`ColumnMajor`、
B=`RowMajor`，4×8 lane lattice 与 `RowMajorInterleaved<2>`，LaneM/LaneN 均为 4。
源码见[官方 SM80 DefaultMmaCore](https://github.com/NVIDIA/cutlass/blob/v3.5.1/include/cutlass/gemm/threadblock/default_mma_core_sm80.h)
及[SIMT warp iterator](https://github.com/NVIDIA/cutlass/blob/v3.5.1/include/cutlass/gemm/warp/mma_simt_tile_iterator.h)。
K30 已采用这一 ownership 的核心结构；该公共特化本身也没有隐藏的 XOR shared 布局。

[公开参考与 cuBLAS 审计](16-公开CUTLASS对照与主循环成本审计.md)显示，二者主循环
同样是每 warp 每 k 6 条有效 LDS、12 waves。这个成本匹配不证明私有 cuBLAS 的完整
ownership、地址生成和 pipeline 与公开实现相同。`256x128_8x4` 的名称不足以
恢复私有布局，更不能据此推断它必定采用 warp specialization。

在“每线程每 k 直接从 shared 获取 A16+B8、最大装载宽度仍为 LDS.128”的范围内，
6 条 load 已达到 `24/4` 的条数下限。若 float4 分组保持不变，单纯对 shared 地址
做双射重排，也不会自动改变哪些 lane 读取同一逻辑元素。当前历史 SourceCounters
的 LDS excessive=0，主循环服务量已与参考匹配，因此本轮 **不新增 shared-layout
变体**。这完成的是基于证据的对照审计，不是漏做一项优化，也不宣称所有可能布局
均已达到理论最优。若未来确有新布局假设，必须同时给出匹配的 ownership/iterator
和可验证的交易成本预测。

A 的普通 shared stores 仍有 16,777,216 excessive waves，见
[历史 memory-instructions.csv](../results/k30-20261013/source/memory-instructions.csv)。
这与 shared-load 的结论不同；cuBLAS 的 LDGSTS 又不完整计入普通 STS 计数，不能
用普通 store 表推导“cuBLAS 写 shared 没有成本”。本轮不把这一观察扩展为新布局搜索。

## 5. K31 版本与因果边界

所有 K31 版本复用 K30 的 `Shape`、`SharedLayout`、`FragmentIterator`、`compute`
和 `epilogue`。默认 BM/BN/BK=128/128/16，128 threads；每次只改变下表所列因素。

|模式|CTA / threads|shared stages|相对谁、改变什么|
|---|---|---:|---|
|`k30`|128×128 / 128|2|原始 K30 V2，对照|
|`control`|同上|2|K31 分离封装，行为对照|
|`late`|同上|2|相对 control：把下一 tile 的 load 显式放在 compute 后，缩短源码临时生命周期|
|`vectors`|同上|2|相对 late：逐 float4 读取后写 shared，研究临时 fragment 的组织|
|`stage3`|同上|3|相对 control：只增加一个 shared stage|
|`stage4`|同上|4|相对 control：只扩展 shared ring，作为已知资源压力的对照|
|`cta256`|256×128 / 256|2|相对 control：CTA 沿 M 扩展；保留 64×64 warp、ownership、双阶段协议|
|`r220/r225/r230/r235/r240`|128×128 / 128|2|相同主体的编译器寄存器上限诊断|

用户所说“当前 K30”和“2-stage”指向同一基线，故以 `k30/control` 验证封装等价，
不虚构两个不同的 pipeline。新的 stage 对照是 3-stage 与 4-stage。
256-thread 版本继续使用 8 个 64×64 warp，覆盖 256×128；每线程仍为
128 个 accumulator。它检验的是现有 ownership/协议下的大 CTA，不冒充完整 cuBLAS。

生命周期对照在源码上的顺序为：

```text
control：load future → compute current → store future → barrier
late：   compute current → load future → store future → barrier
vectors：compute current → [load float4 → store float4] × vectors → barrier
```

编译器可以移动以上普通内存指令；局部变量作用域不等于物理寄存器生命周期。
`next` 寿命缩短后的实际代价要由 ptxas/SASS 和测量共同判断。
所有版本沿用同一 stage 发布/回收协议：初始化 S−1 个 ready tile，本轮 current 与
future slot 不同，末尾 block barrier 同时结束当前读取并发布 future。
尾部不越界加载，但所有线程继续共同执行 barrier。

220/225/230/235/240 是 `__maxnreg__` **上限**，不是承诺的实际分配数。
上限放宽也不保证分配数单调增加，`r235=233`、`r240=231` 就是本轮编译事实。
`__maxnreg__` 不能与 `__launch_bounds__` 联用，所以预算对照使用独立注解入口，
而 control/lifetime/stage 入口保留 launch bounds。不能把预算实验伪装成只改了
某个运行时寄存器数量。

`r220` 出现 8 B stack 和 8 B spill load/store，SASS 也含 LDL/STL，已在资源门槛
淘汰；它是 spill 失败，不是正确性失败，也不参加候选性能排名。
其余编译通过资源门槛的版本继续进入正确性、Sanitizer 与实测接受检查。

上述 shared 是用户分配，不含 NCU 可能报告的平台开销。K10 为静态 shared，
runtime CSV 的 dynamic_shared=0 不代表它未使用 shared。理论驻留容量也不是
测得的 achieved occupancy：2 个 128-thread CTA 或 1 个 256-thread CTA 均为
8 warps 容量。lower-reg 的 late/vectors 没有因此增加理论驻留 block；若性能变化，
不能直接写成“occupancy 提升”。同样，launch bounds 不是运行时必须驻留相应
block 数目的保证。

本轮 strict cuBLAS 的 NCU 资源仍为 202 regs/thread、50,176 B shared/block，
与自写核的“用户 shared 数组”列口径不同；完整测量值保留在 nsight.csv。

## 7. 静态 SASS 对照

`k30` 与 `control` 的规范化 SASS 文本及机器编码完全一致，SHA256 都为：

```text
31db7578045aed41213dada11b20a708eed69a3353034332aa3bc52b6b442338
```

哈希保留了指令编码与控制字段，不只是 opcode 数量相同；依据为
[`analyze_k31_binary.py`](../../scripts/analyze_k31_binary.py)生成的
`static-sass.csv` 和 `sass_k30.txt/sass_control.txt`。这是后续单因素实验的入口检查，
不意味着两个独立进程的计时会完全相同。

|模式|静态总指令|FFMA|LDS|IMAD|IADD3|MOV|
|---|---:|---:|---:|---:|---:|---:|
|K30 / control|3360|2304|96|58|120|21|
|late|3344|2304|96|49|125|26|
|vectors|3360|2304|96|59|120|22|
|stage3|3432|2304|96|69|129|21|
|stage4|3496|2304|96|72|139|21|
|cta256|3344|2304|96|54|120|21|

K31 全部仍为 FP32 SIMT，静态 HMMA/MMA/LDGSTS/DEPBAR 为零。
表中是整个函数的静态数量，包含条件 epilogue 与预填，不是动态执行成本；
不能用 `3360→3344` 直接推断对应百分比的性能提升。

主循环调度 CSV 显示，K30/control 的下一 tile LDG 位于 2046 条 FFMA 之后，
只剩 2 条 FFMA；late/vectors 的 LDG 位于 2032 条 FFMA 之后、剩 16 条。
源码顺序确实影响生成代码，但这些位置仍集中在计算尾部，不能称为覆盖整个 BK
的 load/compute overlap。剩余指令距离也不是 latency 周期数；对 scoreboard、
issue 和吞吐的实际影响必须由下面的测量补齐。

## 8. 实测口径与接受标准

沿用 K30 的独立严格 FP32 harness：同一输入生成方法与 seed=20261013，alpha=0.5，
strict cuBLAS 为 `CUBLAS_PEDANTIC_MATH + CUBLAS_COMPUTE_32F_PEDANTIC + GEMM_DEFAULT`，
运行脚本清除 `NVIDIA_TF32_OVERRIDE`。每次调用前复位同一 C0，复位不计入 GEMM event。
性能为 4096³、beta=3、七轮轮换顺序、每组 warmup=10/repeat=50；NCU 插桩时间
不填入公平性能表。所有新 CSV 使用独立目录，历史实验不覆盖。

资源通过的候选须验证 128/256/512/1024/2048/4096 × beta=0/1/3，保留
absolute error=0.01 并拒绝非有限误差。Sanitizer 工具、具体尺寸、通过数与日志
应逐项保存，不把有限测试描述成任意输入的证明。

性能接受要求是稳定收益、无 spill、正确性与 Sanitizer 通过，并能用 Nsight/SASS
解释执行变化。记录 issue、eligible warps、FP32 pipe、scoreboard、barrier/wait、
DRAM/L2、shared wavefront/conflict、register/local memory 等；单个 counter
变好而 GFLOPS 不变不能判成功。`issue_inst0` 标记为 no-issue，不直接冒充
“no eligible warp”；静态资源预测与 achieved occupancy 分开报告。

完整 no-issue、dispatch、barrier、wait、local sectors 等见
[nsight.csv](../results/k31-20261013/nsight.csv)。

### 9.3 失败方案究竟否定了什么

- **临时生命周期**：235→219→209 regs 均没有增加理论驻留容量。late 的 issue/FP32
  下降；vectors 的 short-scoreboard 从 0.0513 增到 0.1321。源码临时对象更短、
  静态指令稍少，没有产生更好的执行节奏。当前证据不能进一步声称“少了几个寄存器
  就损失了精确多少 ILP”，也不能把全局加载集中到计算尾部误说为新实现了长距离重叠。
- **3-stage**：仍有两个 CTA、occupancy 仍约 16.5%，不能用驻留减半解释 −1.11%。
  long-scoreboard 升至 0.2549，issue 下降；源码 lookahead 更远，机器码 LDG 仍只
  留下 2 条 FFMA。更多 stage 降低了一次冷缓存 DRAM 测量值，却没有改善发射效率。
- **4-stage**：66,560 B 用户 shared 跨过容量阈值，只能驻留一个 128-thread CTA。
  occupancy 约 8.33%，eligible 只有 0.598，是明确的资源损失。barrier/wait 指标
  降低不能抵消 −24.09% 的真实回退，不能把它包装成同步优化成功。
- **256-thread**：49,664 B shared、225 regs、一个 8-warp CTA，occupancy 恢复至
  16.65%，但 issue 69.30%、long-scoreboard 0.3348。DRAM 更少仍慢 13.01%。
  此时问题不是“warp 数量少”，而是当前大 CTA 的搬运/同步/计算组合没有保持就绪。
  同 CTA 内相位集中是待验证解释，不能冒充已隔离的因果；不否定所有 256-thread 设计。
- **寄存器预算**：r220 spill 淘汰；r225/r230 无 spill 仍慢；r235/r240 留下小幅
  正向均值，但 issue 未一致改善，未通过预先约定的接受标准。不能把 K30 的 235
  定义成数学最优，也不能把寄存器降得越低当作优化目标。

## 10. 剩余差距与下一步

**K31 没有把 K30 推到 98%。** 七轮 K30 为 strict 的 96.297%，独立五轮为
96.439%；最接近的 r240 为 96.899%/96.667%，仍未通过稳定且有硬件解释的接受门槛。
因此保留 K10 默认实现、K30 V2 研究基线，K31 全部作为受控实验保存。

剩余差距的优先级不是耗时分账，更不能将以下 counter 相加得到 3.7%：

1. **数据就绪与指令调度的协同，证据最强。** 同 occupancy 下，strict 的 issue
   87.44% 对 K30 83.18%，eligible 1.583 对 1.381；long-scoreboard 0.0224 对
   0.1802，wait 0.0122 对 0.0673。结合 K30 的 LDG 仍集中在 FFMA 尾部，说明下一步
   应解释具体 producer→consumer 的等待，而不是再把 stage 数加一。
2. **寄存器分配/存活期，只有小收益线索。** r235/r240 值得保留为诊断对照，
   但显式缩短生命周期的两版都慢。分配数量、register reuse/control 字段与指令顺序
   必须一起看；本轮没有测得寄存器 bank conflict，不能凭 FFMA 寄存器编号宣布这一原因。
3. **CTA 复用与搬运协议的协同，尚未隔离。** cuBLAS 冷缓存 DRAM 更少，包含集成的
   LDGSTS/DEPBAR；但是更大的 cta256 已经减少 DRAM 仍慢，不能唯一归因于流量。
   它值得在明确的数据就绪模型之后研究，不值得立即再扩大 tile。
4. **纯 shared-load layout，当前优先级低。** 逐 PC 主循环已匹配 6 LDS/12 waves，
   无额外 LDS wavefront；整核 counter 的小量非零已在上文保留。现有证据没有要求再做 permutation；ordinary A-store 的代价
   与 global→shared 搬运仍需区分，不能把它和 fragment-load 混成一个 layout 问题。

关于五个设计维度的结论是：**fragment ownership 已由 K30 验证了交易成本改善；
shared-load layout 本轮没有新的可减少成本；stage 数量和 CTA 外形单独扩展失败；
寄存器 lifetime 的两个显式改写失败。剩余差距仍支持多因素联合的时间组织问题，
不支持某个缺失的“小技巧”。** cuBLAS 的低 long-scoreboard 与高 issue 是待解释
事实，而非私有实现细节的证据；不能从名称推断 warp specialization。

如果目标是 98%–100%，下一步最多保留两项，按顺序做，不并行堆叠：

1. **先完成 load-use 时序归因。** 固定 K30 V2，用逐 PC 计数找到末尾 LDG→STS
   等待及 barrier 周围停顿；与 strict 的 LDGSTS/DEPBAR 对照，区分样本集中点、
   动态执行次数与等待周期。若修改，只改变一组加载/消费的距离，并先确认 SASS
   真的移动、无 spill、没有改变数学顺序，再测吞吐。普通源码“提前加载”若被 ptxas
   下沉就立即停止该变体，不继续加 buffer。本轮尚不能承诺这会带来 1.7 个百分点。
2. **只有第一项形成可验证假设，才重新评估大 CTA。** 冻结已解释的搬运/同步协议，
   再做 128/256-thread 对照，观察能否在降低流量的同时保持 eligible/issue；
   否则保留 128-thread。不复制私有 cuBLAS，不做 tile/stage 暴力搜索。

这一步的研究价值是划清边界：96% 之后不再把“资源更省”当成“微内核更好”。
优化故事的完整回顾见 [从 90% 到 96%](06-RTX3080-K10优化故事.md)。

合法 float4 对齐、A/B/C 不重叠。没有宣称任意尾 K/stride 或任意矩阵形状均已验证。

代码 diff 的核心是独立 `k31::run<Shape,Stages,Policy>`：K30 control 的主体等价；

cta256 只扩 M/threads；寄存器预算使用独立 `__maxnreg__` 注解入口。
