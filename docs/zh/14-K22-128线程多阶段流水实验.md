# K22：128-thread、BK=8 多阶段流水实验

日期：2026-10-12

环境：RTX 3080 10 GB（SM86）、CUDA 12.4、驱动 550.127.05、Nsight Compute
2024.1。输入、计时和 strict FP32 口径与 K21 报告一致；`NVIDIA_TF32_OVERRIDE`
未设置，参考为 `CUBLAS_COMPUTE_32F_PEDANTIC`。

## 1. 实验问题与冻结条件

K22 不修改 K10，只回答一个问题：在 K10 的 128-thread 输出 ownership 上，BK=8
多阶段流水能否解释 cuBLAS 的优势？以下条件全部冻结：

- CTA tile：128×128；
- 128 threads、4 warps；
- warp tile：64×64；
- lane 映射：`threadRow=lane/4`、`threadCol=lane%4`；
- 每线程 8×(4×4)=128 个 accumulator；
- A shared layout：转置的 `[k][m+4]`；
- B shared layout：`[k][n]`；
- epilogue 和 `alpha/beta` 计算。

只改变 BK 和 stage 组织：

| 版本 | BK | slots/stages | 搬运 | 目的 |
|---|---:|---:|---|---|
| K10 | 16 | 1 | 同步 float4→register→shared | 基线 |
| V1 | 8 | 2 | 同步 ping-pong，无重叠 | 隔离 BK=8；总 shared 容量保持与 K10 相同 |
| V2 | 8 | 2 | `cp.async` stage ring | 测量两阶段 overlap |
| V3 | 8 | 4 | `cp.async` stage ring | 测量四阶段时间深度 |

V1 仍严格执行 `load → barrier → compute → barrier`；两个槽只轮换，不提前搬运。
V2/V3 的 A 使用 4-byte `cp.async` 直接写入 K10 的转置加 padding 布局，B 使用
16-byte `cp.async`。因此没有为了 async copy 把 A 改回 K21 V2 已证明有冲突的
row-major shared layout。

源码见 [22_kernel_multistage_pipeline.cuh](../../src/kernels/22_kernel_multistage_pipeline.cuh)。

## 2. 正确性与资源

V1/V2/V3 在 128、256、512、1024、2048、4096 以及 `beta=0/1/3` 下共
54/54 PASS；原始 absolute error 阈值仍为 0.01。Compute Sanitizer 对每个版本的
128 和 256 尺寸共 6/6 PASS。

| 模式 | Registers/thread | ptxas shared | NCU shared | Achieved occupancy | spill |
|---|---:|---:|---:|---:|---:|
| K10 | 184 | 16,640 B | 17.664 KB | 16.57% | 0 |
| V1 | 179 | 16,640 B | 17.664 KB | 16.25% | 0 |
| V2 | 161 | 16,640 B | 17.664 KB | 24.43% | 0 |
| V3 | 161 | 33,280 B | 34.304 KB | 16.57% | 0 |
| strict cuBLAS | 202 | 不可由 ptxas 取得 | 50.176 KB | 16.66% | 0 |

三个 K22 版本都低于 220 registers/thread，且没有 local-memory load/store。
V2 因寄存器和 shared 都较低，可以达到约三个 CTA/SM；V3 的四份 shared stage 又把
它压回约两个 CTA/SM。这个资源变化本身就是四阶段实验的一部分，不能把 occupancy
相同或更高直接解释为吞吐更高。

## 3. 三轮交错性能

口径：4096³、`alpha=0.5`、`beta=3`、固定 seed、每次复位 C、10 次预热、50 次
计时，三轮轮换执行顺序。

| 模式 | 平均 GFLOPS | 范围 GFLOPS | 平均时间 | 相对 K10 | strict 比例 |
|---|---:|---:|---:|---:|---:|
| strict FP32 cuBLAS | 21,643.5 | 21,544.3–21,797.5 | 6.350 ms | +10.15% | 100.00% |
| K10 | 19,649.9 | 19,588.0–19,712.6 | 6.994 ms | 基线 | 90.79% |
| K22 V1 | 17,276.5 | 17,252.2–17,293.2 | 7.955 ms | -12.08% | 79.82% |
| K22 V2 | 17,307.6 | 17,275.2–17,329.3 | 7.941 ms | -11.92% | 79.97% |
| K22 V3 | 16,103.8 | 16,013.7–16,208.6 | 8.535 ms | -18.05% | 74.41% |

V2 相对 V1 只有 +0.18%，低于“主要瓶颈被解除”应有的幅度。V3 相对 V2
下降 6.96%。所以不能把 BK=8 或四阶段流水接受为 K10 的优化。

## 4. Nsight Compute：流水做对了什么，又付出了什么

| 指标 | strict | K10 | V1 | V2 | V3 |
|---|---:|---:|---:|---:|---:|
| Issue slots busy | 87.35% | 79.12% | 67.20% | **78.33%** | 70.11% |
| No eligible | 12.65% | 20.88% | 32.80% | **21.67%** | 29.89% |
| Eligible warps/scheduler | 1.580 | 1.355 | 1.118 | **1.772** | 1.097 |
| FP32 pipe active | 78.56% | 73.53% | 60.97% | 64.25% | 57.52% |
| Long scoreboard | 0.023 | 0.084 | 0.322 | **0.057** | 0.048 |
| Short scoreboard | 0.083 | 0.029 | 0.126 | 0.249 | 0.235 |
| L2 hit rate | 87.80% | 77.33% | 48.62% | 75.40% | 75.67% |
| DRAM read | 516.5 MB | 972.7 MB | 1,991.7 MB | 1,083.8 MB | 971.9 MB |
| Dynamic instructions | 2.402 B | 2.336 B | 2.378 B | **2.688 B** | 2.690 B |
| Dynamic LDGSTS | 25.31 M | 0 | 0 | 20.97 M | 20.97 M |
| Shared-load conflicts | 0 | 0 | 0 | 0 | 83.5 K |
| Shared-load wavefronts | 201.90 M | 335.55 M | 335.55 M | 335.55 M | 335.63 M |

### 4.1 BK=8 同步版本为什么慢

V1 把 K tile 数量加倍，也把 CTA barrier 和循环控制的动态频率加倍。更重要的是，
K10 的 A float4 搬运让一个 warp 每次覆盖 8 行、每行连续 64 B；BK=8 后变成 16 行、
每行连续 32 B。数学字节数不变，但 transaction 聚合和跨 CTA 的缓存时序发生变化。
实测 L2 hit 从 77.3% 降到 48.6%，DRAM read 约翻倍，long scoreboard 从 0.084
升到 0.322。BK 小不是免费午餐。

### 4.2 两阶段 pipeline 是否真的隐藏了延迟

是，但只在局部意义上成立。V2 相比 V1：

- L2 hit 恢复到 75.4%，DRAM read 降回约 1.08 GB；
- long scoreboard 降至 0.057；
- issue 从 67.2% 恢复到 78.3%；
- eligible warps 从 1.118 提升到 1.772。

因此不能说 `cp.async` 完全无效。但 V2 动态指令达到 2.688 B，比 K10 多约 15.1%。
原因包括转置 A 所需的 4-byte `LDGSTS`、两倍 K-loop 控制、stage 地址和 wait/commit
协议。它虽然更常有 eligible warp，却把更多 issue slot 用于搬运和控制，FP32 active
只有 64.3%，仍低于 K10 的 73.5%。最终只比 V1 快 0.18%，而比 K10 慢 11.9%。

### 4.3 四阶段为什么更慢

V3 与 V2 执行相同数量的动态 `LDGSTS` 和近似相同的总动态指令，但 shared 从
17.664 KB 增到 34.304 KB，使 occupancy 从 24.4% 回落到 16.6%。BK=8 的两阶段已经
把 long scoreboard 压低；额外 stage 没有新的长延迟可隐藏，却减少可驻留 CTA，导致
eligible warp 降到 1.097、issue 降到 70.1%、FP32 active 降到 57.5%。

Shared-load conflict 仍接近零，所以 V3 失败不是传统 bank conflict；是 stage 深度、
ready-warp 数量和额外指令的资源交换失败。

## 5. SASS 边界

| 模式 | 静态指令 | FFMA | LDS | LDGSTS | DEPBAR | BAR | IMAD | IADD3 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| K10 | 2,768 | 2,176 | 96 | 0 | 0 | 2 | 20 | 26 |
| V1 | 1,672 | 1,152 | 48 | 0 | 0 | 2 | 16 | 28 |
| V2 | 1,440 | 512 | 33 | 32 | 2 | 3 | 65 | 125 |
| V3 | 2,016 | 768 | 57 | 52 | 2 | 3 | 106 | 186 |

静态 FFMA/LDS 数量不能直接当成数学工作量，因为 ptxas 对各版本的 K loop 展开程度
不同；动态 FMA 计数才表明它们完成了相同主计算。SASS 的可靠结论是：V2/V3 确实
生成 `LDGSTS`、`LDGDEPBAR/DEPBAR`，而且整数地址/控制指令明显增加。失败不是
“编译器没有生成 async copy”。

## 6. 五个问题的回答

### 6.1 多阶段 pipeline 是 K10 到 cuBLAS 差距的主要因素吗？

**不是单独的主要因素。** 两阶段 pipeline 能修复 BK=8 同步版本的大部分
scoreboard/issue 退化，但不能超过 K10，四阶段还会倒退。cuBLAS 的多阶段流水必须和
CTA shape、transaction layout、fragment iterator、寄存器生命周期一起工作。

### 6.2 BK=8 是否比 BK=16 更适合 RTX 3080 SIMT FP32？

**不能脱离微内核结构这样判断。** 在冻结的 128-thread K10 ownership 中，BK=8
同步版比 K10 慢 12.1%；最好的 BK=8 两阶段版仍慢 11.9%。cuBLAS 选择 BK=8，只能
证明 BK=8 适合它的 256-thread、四阶段和 layout 组合，不能证明它对 K10 单独更优。

### 6.3 四阶段 pipeline 是否提高 issue slots？

**没有。** V3 为 70.11%，高于同步 V1 的 67.20%，但低于 V2 的 78.33% 和 K10 的
79.12%。增加第三、第四 stage 的边际收益不足以补偿 shared 导致的驻留 CTA 减少。

### 6.4 如果 K22 成功，应如何扩展到 256-thread？

正确顺序应是保持 BK=8、stage layout 和 wait/commit 协议不变，只把 CTA M 扩展到
256 并增加到 8 warps，然后重新分配每个 warp 的输出 ownership；每一步检查寄存器、
shared transaction 和 issue。不能同时更换 fragment layout 和 epilogue，否则无法知道
收益来源。

但本次 K22 **没有成功**，所以不应把这套 128-thread pipeline 原样放大。下一版必须先
设计 256-thread CTA 下的 global-copy/shared-layout/warp-iterator 共同映射，让更多计算
摊薄每 tile 的 async 和 barrier 成本。

### 6.5 失败后，cuBLAS 优势属于 A/B/C/D/E 哪一项？

答案是 **E：多因素联合**。证据排序为：

1. CTA shape 与工作量摊销：128-thread、BK=8 的循环/搬运开销过高；
2. pipeline 与资源平衡：两阶段改善等待，四阶段却降低 ready-warp 供给；
3. global/shared transaction layout：同步 BK=8 的 L2/DRAM 明显恶化；
4. fragment iterator 和指令调度：V2 issue 接近 K10，但 FP32 active 仍低，说明 ready
   warp 并未持续发出足够 FFMA。

K22 排除了“只给 K10 加四阶段流水就能从 91% 提到 95%”这个假设。下一步如果继续，
应建立新的 256-thread、BK=8、四阶段 micro-kernel，但把 CTA ownership、async copy
粒度、permuted shared layout 和 fragment schedule 作为一个设计单元，而不是从 K22
机械扩容。
