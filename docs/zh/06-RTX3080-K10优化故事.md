# 从 90% 到 96%：RTX 3080 上的 SIMT SGEMM 微内核优化故事

实验始于 2026-10-10；本篇已补充至 2026-10-13 的 K31 精修与因果审计。

硬件与软件：RTX 3080 10 GB（SM86）、CUDA 12.4、Nsight Compute 2024.1。
主问题：怎样在不改变 FP32 计算路径、不牺牲正确性、不挑选偶然峰值的前提下，
让一个教学用 SGEMM kernel 稳定接近同口径 cuBLAS？

## 1. 故事现在走到了哪里

目前最有意义的进展是：K30 V2 在同一台 RTX 3080 上达到 **20.801 TFLOPS、
同轮 strict FP32 cuBLAS 的 96.33%**，比 K10 提高 5.85%；独立追加三轮仍为
**96.25% cuBLAS、比 K10 高 5.62%**。这发生在多轮局部改动失败之后。
K31 后续七轮又测得 K30 为 **96.30% cuBLAS**，复现了这一级别；资源上限微调
留下约 0.2% 量级的小收益信号，但尚无达到 98% 的证据。K10 仍保留为稳定默认
实现，K30 是独立研究入口。

最初更大的 tile、更高的 occupancy、双缓冲、异步复制、缓存重排都显得有希望。
实验逐步揭示：它们改变的成本不同，而且会相互影响。某个具体实现失败，只能否定
它在当时条件下的收益，不能把整类设计方向永久排除。

贯穿故事的线索是：**从整块 GPU 的利用率，追到每条 shared load 服务哪些数据，
再把 fragment 的读取方式与安全的同步协议一起设计。** K30 没有使用 Tensor Core，
没有放宽 0.01 绝对误差门槛，也没有靠单次最高分来宣布突破。较低的 shared 服务成本
与双缓冲的单次 barrier 组织结合，才把指标变化转化成可重复的吞吐收益。

下文按发生顺序保留当时的数据、判断和修正。不同实验的绝对 GFLOPS 不直接拼接；
每个相对百分比都使用同一轮的 K10 或 cuBLAS 基线。文中的 `no-issue` 指无指令发射
周期比例，来自 `issue_inst0`，不能直接等同于“没有 eligible warp”。

## 2. 第一幕：先纠正目标，而不是先改 kernel

最早的目标被表述为达到原作者报告的“106%”。核对后发现，原作者 A6000 数据中
K10 是 21,779.3 GFLOPS，cuBLAS 是 23,249.6 GFLOPS，实际为 **93.7%**。超过 100%
的数字来自不同机器、轮次或口径的交叉相除，不能作为优化目标。

同时，仓库原 benchmark 在 `beta=3` 时会连续更新 C。如果候选运行次数、初始 C、
预热状态不同，结果既不利于数值比较，也可能引入不同的缓存前置状态。因此我们先
修实验框架：

- 固定随机 seed；
- 每次预热和计时调用前恢复相同的初始 C，恢复 copy 不计时；
- 使用相同的 4096³、`alpha=0.5`、`beta=3`；
- 预热 10 次、计时 50 次、三轮交错执行；
- 自写 kernel 对照 pedantic strict FP32 cuBLAS；
- 保留原绝对误差 0.01 与 NaN 检查；
- 把显式 TF32 独立成另一条对照线，不与 CUDA Core FP32 混算。

这个步骤本身没有让 kernel 更快，却让后面的每个百分比有了明确含义。

## 3. 第二幕：先找出真正最快的自写核心

编号更大不代表性能更高。在相同 4096³、10 次预热和 50 次计时口径下，早期筛选为：

| Kernel | 主要思路 | GFLOPS |
|---|---|---:|
| K9 | autotuned 2D tiling | 17,063.2 |
| **K10** | **warp tiling** | **19,197.7** |
| K11 | double buffering | 17,252.8 |
| K12 | async-copy double buffering | 15,827.7 |

所以后续没有把“最新编号”当作默认胜者，而是以 K10 为稳定基线。它的最终主体配置是：

```text
BM=128, BN=128, BK=16
WM=64,  WN=64,  WNITER=4
TM=8,   TN=4,   NUM_THREADS=128
AS_PAD=4, MIN_BLOCKS=2
```

24 组 tile 搜索覆盖 `BK=8/16/32`、128/256 threads、方形与非方形 block/warp tile。
当时 128×128×16 配置仍然胜出。128×256、256×128 等更大 tile 因寄存器压力或 spill
严重回退，说明“增加复用”只有在资源成本可控时才成立。

## 4. 第三幕：两个小改动为什么有效

### 4.1 Padding：减少可测量的 shared-store 冲突

K10 把 A tile 转置写入 shared memory。原 `As[BK][BM]` 在 `BM=128` 时让多个 lane
映射到相同 bank。把 stride 改成 `BM+4` 后：

| 指标 | `AS_PAD=0` | `AS_PAD=4` | 变化 |
|---|---:|---:|---:|
| Shared-load conflicts | 0 | 0 | 不变 |
| Shared-store conflicts | 50.33 M | 16.78 M | -66.7% |
| Shared-store wavefronts | 83.89 M | 50.33 M | -40.0% |

Padding 不是越大越好。1/2/3 明显回退，4 与 12 接近，所以选择额外 shared 占用更小
的 4。它没有消灭所有冲突，却是一个由计数器解释、由 benchmark 筛选的改动。

### 4.2 Launch bounds：允许更多寄存器，反而更快

单参数 `__launch_bounds__(128)` 使用 168 registers/thread。改成
`__launch_bounds__(128, 2)` 后，ptxas 使用 184 个寄存器且没有 spill，受控均值相对
单参数版本提高约 2%。这看似违背“寄存器越少、occupancy 越高越好”，但实际说明：

- K10 需要足够寄存器保存大量独立累加器；
- 168 registers 的版本理论 occupancy 更高，却执行更多指令，Profiler duration 更长；
- 184 registers 仍能容纳两个 128-thread block/SM；
- `minBlocks=2` 是编译器资源目标，不是运行时驻留保证。

继续压到 `minBlocks=3` 会回退到约 17.4 TFLOPS；`minBlocks=4` 产生 816 B stack spill，
只剩约 0.735 TFLOPS。这里最重要的经验不是“184 是神奇数字”，而是 occupancy 必须和
指令数、spill、issue efficiency 一起看。

## 5. 第四幕：先把 cuBLAS 的精度身份说清楚

原 kernel 0 使用 `CUBLAS_COMPUTE_32F` 和名为 `CUBLAS_GEMM_DEFAULT_TENSOR_OP` 的
algorithm，但 Nsight 显示实际选择的是 SIMT SGEMM：Tensor pipe 为 0，主要执行普通
FP32 FMA。严格入口 13 也选择相同 SIMT 路径，固定输入逐元素 bit-equal。

显式 TF32 入口 14 达到约 29.77 TFLOPS，但使用 Tensor Core，并且 16,777,216 个
元素中有 14,850,391 个超过原 0.01 误差阈值。它可以作为“改变精度后能有多快”的
对照，却不能写成 K10 的同精度优化。

公平三轮基线最终为：

| 实现 | 平均 GFLOPS | 相对 strict FP32 |
|---|---:|---:|
| strict FP32 cuBLAS | 21,704.9 | 100.00% |
| K10 | 19,696.5 | **90.75%** |
| 显式 TF32 cuBLAS | 29,771.3 | 精度路径不同，不参与比例 |

早期完整六尺寸验证得到 19,560.0 对 21,659.9 GFLOPS，即 90.31%；不同轮次的绝对值
略有变化，但都支持“K10 稳定在同口径 cuBLAS 的约 90%”这一阶段结论。不能从不同轮次各挑一个
最高值重新组合百分比。

## 6. 第五幕：为什么“双缓冲”没有自动变快

双缓冲的目标是计算当前 K tile 时加载下一 tile，从而隐藏 global-memory 延迟。但
K11/K12 的具体实现没有实现这个净收益：

| 指标 | K10 | K11 | K12 |
|---|---:|---:|---:|
| 公平平均 GFLOPS | 19,696.5 | 16,977.1 | 15,702.7 |
| Registers/thread | 184 | 170 | 210 |
| Shared/block | 16.64 KB | 49.15 KB | 32.78 KB |
| FMA pipe active | 73.64% | 58.69% | 55.41% |
| Issue slots busy | 79.14% | 65.92% | 62.82% |
| No-issue | 20.92% | 34.05% | 37.19% |
| Shared conflicts | 16.78 M | 25.17 M | 217.25 M |

K11 虽减少 DRAM read，却引入 256 threads、49 KB shared、半 block 分工和更多全 block
同步。K12 的多个 4-byte async copy、C++ barrier、双份 shared 和 210 registers 又把
资源与指令开销推得更高。所谓“双缓冲”只描述结构，不保证 load 真正被 FFMA 覆盖。

当时由此提出了更窄的问题：在 K10 已有 shared tile 内，把下一组 fragment 更早
装入少量寄存器，是否就能填补 issue 空洞？后来的 K19 专门验证了 B fragment 预取，
结果仍然失败；再后来的 K30 则用不同 fragment ownership 与同步协议获得了收益。
因此 K11/K12 的失败保留为具体实现的反例，不再被概括成“双缓冲无效”。

## 7. 第六幕：Grid Swizzle 验证了一个很诱人的错误假设

K10 相比 cuBLAS 有更多 DRAM read、更低 L2 hit，因此一个合理假设是：如果改变 block
到 C tile 的映射，让相邻 block 更容易复用 B tile，就可能缩小差距。

为此新增 K15，只改变 grid mapping，数学主体、累加顺序、tile、padding 和 launch
bounds 全部复用 K10。K10 重构前后 cubin SASS hash 完全一致。五个
`GROUP_M=1/2/4/8/16` 完成 90 个正确性组合和 Compute Sanitizer 检查。

正式三轮结果为：

| 方案 | 平均 GFLOPS | 相对 K10 |
|---|---:|---:|
| K10 | 19,688.9 | 基线 |
| K15 G1 | 19,666.2 | -0.12% |
| K15 G2 | 19,634.6 | -0.28% |
| K15 G4 | 19,606.6 | -0.42% |
| K15 G8 | 19,522.7 | -0.84% |
| K15 G16 | 19,454.9 | -1.19% |

最关键的反例来自 G16：

| 指标 | K10 | G16 |
|---|---:|---:|
| L2 hit rate | 76.69% | **86.62%** |
| DRAM read | 962.5 MB | **563.1 MB** |
| Issue slots busy | **79.20%** | 77.62% |
| No-issue | **20.76%** | 22.42% |
| FMA pipe active | **69.53%** | 68.87% |

也就是说，G16 将 DRAM read 减少约 41.5%，性能却下降 1.19%。这不是 swizzle
“完全没作用”；它成功改变了缓存行为，却没有提高吞吐。这否定了“只改善这些 block
的 L2 复用就能加速 K10”的假设。它不能证明所有外存访问成本都不重要，但足以让
后续实验停止继续搜索 GROUP_M，转而研究 issue 和片上数据供给。

## 8. 第七幕：四次局部试验把问题收紧，也暴露了推论边界

K10 此时使用 184 registers/thread、16,640 B 用户 shared，没有 spill，实测 occupancy
约 16.6%。DRAM throughput 约 17.4%，issue 约 79.2%，所以没有显存带宽饱和的迹象。
但低带宽利用率本身不能排除访问延迟、指令或同步成本，后续仍需要逐项验证。

2026-10-11 的四组实验结果如下；百分比各自相对其同轮 K10：

| 实验 | 具体改变 | 结果与有效结论 |
|---|---|---|
| K16 | Shared A 的 K 相关 XOR | 最好仍 −18.35%；把原本为零的 shared-load conflict 引入读取路径 |
| K17 | B-only `cp.async` | 恢复 BK 完全展开后仍 −7.23%；该异步搬运方案没有净收益 |
| K18 | 五种 lane/fragment 变体 | 最接近者 +0.012%，属于噪声；测试范围未覆盖后来完整的 A16/B8 ownership |
| K19 | B fragment 预取、地址提前、K loop 展开 | 全部 −6.30% 至 −7.36%；V1/V3 SASS 完全一致，源码顺序不等于机器调度顺序 |

K19 的 issue 从 79.27% 降到 69.54%–71.51%，FP32 pipe 从 73.71% 降到
64.67%–66.25%，而 LDS 数量与 shared-load wavefront 没变。ptxas 已经在 K10 中
交织 LDS/FFMA；手工增加 B fragment 寿命反而破坏了原有平衡。

这几次失败让我们停止重复这些局部参数，却也留下了一个需要纠正的说法：
**“shared-load conflict 为零”不等于“shared→register 已经没有可节约的成本”。**
当时还没有逐条 LDS 分析必要的 wavefront 数，后来突破恰好来自这个缺口。

## 9. 第八幕：看见 cuBLAS 的形状，还不等于理解它

2026-10-12 的实际 profile 找到 strict FP32 cuBLAS 使用
`cutlass_80_simt_sgemm_256x128_8x4_nn_align1`。它是 CUDA Core SIMT；
256 threads/block、202 registers/thread、49,152 B 用户 shared。NCU 报告的
50,176 B 还包括 1,024 B 平台开销，不能混成源码的 shared 数组大小。

公开 CUTLASS 命名规则中的 `8x4` 指 **BK=8、4 stages**，不是每线程只有 8×4
accumulator。与此同时，名称和资源算术仍不能证明 cuBLAS 私有实现每层 ownership，
也不能证明它存在专职 producer/consumer warp。

两者 occupancy 都约 16.6%，但 cuBLAS issue 约 87%、K10 约 79%。于是 K20
尝试 256-thread CTA，包括两种 one-pass warp tile 与分两次 K traversal 的
64-accumulator 版本。首次三轮结果为：

| 模式 | GFLOPS | 相对同轮 K10 |
|---|---:|---:|
| K10 | 19,618.1 | 基线 |
| K20 V1，64×64 warp | 16,864.3 | −14.04% |
| K20 V2，128×32 warp | 17,093.5 | −12.87% |
| K20 V3，分阶段 accumulator | 16,286.1 | −16.98% |

同一 GPU 独立复测得到相同排序。V1/V2 从两个 4-warp CTA 变成一个 8-warp CTA，
没有增加每 SM 的活跃 warp；实测 issue 降至约 64.5%，long-scoreboard 上升。
同一 CTA 的同步相位更集中，是与这些观察一致的解释，但该实验没有单独隔离这项
因果。V3 occupancy 接近翻倍，却因重复搬运和同步而更慢。

K20 因此回答了一个明确问题：**扩大 CTA 或分批 accumulator 的资源算术正确，
不代表它们的时间组织高效。** 所有输出并非必须同时放在寄存器，但省下寄存器的
方案仍需支付重新遍历 K、搬运或写回的成本。

## 10. 第九幕：iterator 有小收益，多 stage 有真实成本

K21 把问题拆成两部分。V1 只把 K10 的 **shared fragment 索引**改成
`load()/advance()` iterator，保持 global loader 和输出 ownership。七轮平均从
19,607.1 升至 19,738.0 GFLOPS，约 **+0.667%**。这是 shared→register 的地址
组织试验，不应回顾成“Global Iterator 已证明有效”。

它没有减少 FFMA 或 LDS，动态总指令减少约 1.16%；IMAD 减少而 LEA 增加。
issue 和 FP32 active 也没有一起提高，所以这个小收益说明编译后的工作量略少，
不能被包装成解决了 scheduler 的主要问题。

K21 V2 用 256 threads、BK16×2 stages、约 48 KiB shared 来接近 cuBLAS 的
容量，结果只有 16.425 TFLOPS。row-major shared A 便于异步直写，却让 fragment
读取出现约 201 M bank conflicts，寄存器升至 255。相同 shared 容量并没有产生
相同数据通路。

K22 随后冻结 K10 ownership，用 BK8、同步 ping-pong、两阶段和四阶段分别测试。
三轮结果为 K10 19.650、V1 17.277、V2 17.308、V3 16.104 TFLOPS。
两阶段相对同步 BK8 版本明显改善 long-scoreboard、eligible warps 和 issue，
却只快 0.18%：更细的 A 异步拷贝、双倍 K tile 数和 stage 控制让动态总指令比 K10
多约 15.1%，更多发射机会没有变成足够的 FP32 工作。四阶段还减少了可驻留 CTA。

这段的结论是具体的：K10 ownership 下这一套 BK8 流水无法跨过 95%。它并未证明
pipeline 不重要，更不能推出 stage 越深越接近 cuBLAS。

## 11. 第十幕：K23 结束地址公式搜索，逐 PC 审计找到新变量

K23 保持 lane/output ownership，只重排 shared 物理地址。B fragment 分组的 V2
相对同轮 K10 −3.96%，A warp 分组的 V3 −2.10%；后来独立七轮的 A+B 组合 V4
为 −5.22%。它们仍无 shared-load bank conflict，却没有减少读取 wavefront，
并把 shared-store conflict 从约 16.78 M 增至 33.55/50.33/67.11 M。

这使我们停止继续组合地址公式，转向一个可公开检查的参考：CUTLASS v3.5.1 的
256×128、BK8、4-stage SIMT kernel。它七轮为 **19.956 TFLOPS、92.65% cuBLAS**，
高于同轮 K10，但仍没有达到 95%；寄存器 254，明显多于 cuBLAS 的 202。
公开库参数相近并不等于复现私有 cuBLAS 的实现。

真正推动下一步的是逐 PC 的 LDS 成本：

| 主循环指标 | K10 | 公开 CUTLASS / strict cuBLAS |
|---|---:|---:|
| 每 warp、每 k 的有效 LDS 指令 | 6 | 6 |
| 每 warp、每 k 的 shared wavefront | 20 | 12 |
| Shared-load bank conflict | 0 | 0 |

K10 的 96 个 hot `LDS.128` 位置中，32 个每次需 2 waves，64 个需 4 waves；
参考的 48 个位置全部需 2 waves。96 与 48 来自 BK16 与 BK8，不能说参考少读一半。
**访问宽度与广播结构决定基础服务量；零 bank conflict 只说明没有相应的额外冲突。**

公开参考每个 lane 使用 16 个 A、8 个 B、128 个 accumulator；K10 是 8 个 A、
16 个 B、128 个 accumulator。参考把 M fragment 分成四组，其完整 ownership
没有被 K18 的 `WMITER=1` 变体覆盖，也被 K23 的冻结条件排除。此前的失败没有
验证过这一具体设计变量。

审计同时保留了不利证据：公开参考比 cuBLAS 多约 102.4 M 动态 warp 指令，其中
44.0 M 来自无有效线程的恒假 LDS 位置。普通 LSU shared-store counter 又不能完整
代表 LDGSTS 目的端服务成本。这些发现使结论更精确，但还不足以把耗时差额逐项分账。

## 12. 第十一幕：K30 的组合把 91% 推到了 96%

K30 没有链接 CUTLASS，而是把公开映射思想写成独立 SIMT skeleton：

```text
CTA → 64×64 warp tile → 4×8 lane lattice
    → Shared A/B iterator → 每 lane A16/B8 → 128 accumulator → epilogue
```

它先使用 128×128 CTA、128 threads、BK16 和原有 padded A / 连续 B shared
布局。V1 是单阶段基础；V2 改成双阶段同步协议；V3 增至四阶段；V4 再扩至
256 threads、256×128 CTA。V1 相对 K10 还有分层实现和 epilogue 等结构差异，
不能称为只有一处代码改动的严格消融。

七轮交错、4096³、每次复位 C、相同输入与计时方法的结果：

| 模式 | 平均 TFLOPS | 相对同轮 K10 | 同轮 strict 比例 |
|---|---:|---:|---:|
| strict FP32 cuBLAS | 21.593 | — | 100.00% |
| K10 | 19.652 | 基线 | 91.01% |
| K30 V1，单阶段 | 18.576 | −5.48% | 86.03% |
| K30 V2，双阶段 | **20.801** | **+5.85%** | **96.33%** |
| K30 V3，四阶段 | 15.706 | −20.08% | 72.74% |
| K30 V4，256 threads / 四阶段 | 18.376 | −6.49% | 85.10% |

追加三轮独立确认中，K10 为 19.561、V2 为 20.661、strict 为 21.465 TFLOPS。
V2 仍提高 **5.62%**，达到 **96.25%**。下降的绝对性能基线没有被拿来和
上一组较高值交叉相除。

为什么这次成功？逐 PC 与动态计数给出了两项实质变化：

- 新 ownership 让全部 hot LDS 每次都需 2 waves。在相同动态 LDS 数量下，主循环
  wavefront 从 335.54 M 降至 201.33 M，减少 **40%**。
- 双缓冲使 current 与 future 使用不同 slot，并由一次 barrier 同时完成数据发布
  与旧读者退出；动态 BAR 从 2,097,152 降至 1,052,672，接近减半。

二者都不是“只改好了计数器”的叙述。V2 在 occupancy 仍约 16.5% 时，issue
从 K10 的 79.16% 升至 83.30%，FP32 pipe 从 73.71% 升至 77.49%；稳态 replay
也保留相同改善方向。235 registers/thread、33,280 B 用户 shared、零 spill 的
资源代价被完整保留，没有用放宽正确性来交换性能。

但还有两个必要的反证。第一，V1 已经降低 40% shared 服务量，性能仍然下降，
所以 ownership 自身不足以解释 +5.85%。第二，V2 源码虽然把 future tile 的 load
写在 compute 前，SASS 却把主循环 LDG 下沉到 2046 条 FFMA 之后，仅剩 2 条 FFMA
在后面。**不能声称收益来自大范围 global load/compute overlap。** 当前证据支持
较低 fragment 服务成本、单 barrier 双缓冲组织与资源驻留共同有效，尚未给三者
各自分配因果百分比。

V3 说明容量仍有边界：65 KiB 用户 shared 使 128-thread CTA 只能驻留一个，
occupancy 降至约 8.3%。V4 恢复约 16.6% occupancy，却仍只有约 70.7% issue，
所以大 CTA 没有自动修复搬运与计算节奏。K30 的结论保持为 V2 这一组合有效。

K30 四版加 K10 共 90 项六尺寸、三 beta 正确性检查通过，最大绝对误差
0.000610351562；另有 12 项 memcheck 和 16 项 racecheck/synccheck 通过。
这些检查覆盖规定尺寸，不声称对任意尺寸或输入形式化证明。

## 13. 这段故事改变了什么

项目最初的问题是“怎样让 K10 达到原报告的 106%”，后来变成“为什么稳定停在
90–91%”，现在已有可复测的 **96%** 研究实现。进展来自问题越来越具体：

| 阶段 | 当时的假设 | 实验后留下的认识 |
|---|---|---|
| 基线与 padding | 先加更多优化 | 先保证精度、输入、C 复位与计时可比较，再核实实际冲突 |
| K15–K19 | 改缓存、XOR 或多预取一层就能更快 | 这些具体方案无净收益；指标改善不能替代性能改善 |
| K20–K23 | 接近 cuBLAS 的 CTA、容量或地址形式即可 | 资源形状不能替代完整的数据消费与同步设计 |
| 公开 CUTLASS 审计 | 零 bank conflict 就已没有 shared 余量 | 相同 LDS 数量仍可能需要不同的基础 wavefront |
| K30 | 新 ownership 能否支撑更好的主循环 | 单阶段仍慢；与单 barrier 双缓冲组合后可重复达到 96% |

因此，“K10 剩余约 9% 来自哪里”如今有了比笼统的 instruction issue 更具体的回答：
**K10 的 fragment 服务量和单 shared tile 同步协议是已经找到可改进空间的部分，
它们的协同重构缩小了大部分差距。** 这不证明其余因素无关，也不等于把整个增益
都归给同步。过去 barrier stall 较小，不足以排除改变同步协议后对整体调度的收益。

V2 距同轮 cuBLAS 仍差 3.67%。它的 shared-load 服务量已接近参考，但 issue
仍低约 4 个百分点，冷缓存 DRAM read 与 long-scoreboard 更高。这些是定位线索，
不是可相加的耗时占比。由此产生了 K31 的具体问题：显式晚加载是否生成相同调度，
global 临时 fragment 是否能缩短寿命，资源约束是否能保留吞吐。

## 14. 第十二幕：K31 把 96% 的收益解释得更细，没有把噪声写成 98%

K31 冻结 K30 的 fragment ownership、shared layout 和 FP32 运算，分别测试晚加载、
逐 float4 搬运、编译器寄存器预算、三/四阶段和 256-thread 双阶段。
先保留一个同结构 control，其完整 SASS SHA-256 与原 K30 V2 一致。这让我们能够
识别框架改写是否已经引入变化：七轮 K30 为 20,834.3、control 为 20,821.2 GFLOPS，
相差 −0.063%；同轮 strict 为 21,635.4 GFLOPS。旧结果的 96% 平台再次复现。

这轮最先检验的是 K30 留下的疑问：既然实际 LDG 已被下沉，是否可以在源码中直接
晚加载，顺便释放寄存器？

| 方案 | 实际 registers/thread | 七轮 GFLOPS | 相对同轮 K30 |
|---|---:|---:|---:|
| K30 V2 | 235 | 20,834.3 | 基线 |
| K31 显式晚加载 | 219 | 20,128.7 | −3.39% |
| K31 逐 float4 搬运 | 209 | 19,172.4 | −7.98% |
| K31 三阶段 | 233 | 20,602.5 | −1.11% |
| K31 四阶段 | 233 | 15,815.8 | −24.09% |
| K31 256-thread 双阶段 | 225 | 18,122.9 | −13.01% |

晚加载和逐 float4 确实降低了物理寄存器数，却都更慢。SASS 也没有简单保留原调度：
原 K30 的主循环 LDG 在 2046 条 FFMA 之后，这两版在 2032 条之后；地址指令和寄存器
分配同时变化。源码变量作用域变短，不保证编译器只缩短那一组临时量的生命周期，
更不保证 shared/FFMA 调度不受影响。这个反例否定了“既然硬件已经晚加载，改写源码
就能免费省寄存器”的推论；它没有推翻 K30 的实际同步和 wavefront 证据。

三阶段没有改善吞吐，四阶段再次让 occupancy 约减半。256-thread 双阶段则直接
回答了另一个窄问题：保持已有消费协议、只扩大 CTA，同样无法复现 cuBLAS。
这些数据没有要求我们马上增加更深流水或新 warp 分工，而是再次显示资源容量与
执行节奏必须匹配。

寄存器预算试验更接近噪声边界，也最容易写成过度乐观的故事。预算 220 产生
8 B spill load 与 8 B spill store，按规则退出；没有把该版本放进性能排名。
预算 225/230 的无 spill 版本仍分别回退约 2.43%/2.06%。预算 235/240 实际得到
233/231 registers，而不是预算数字本身，说明编译器资源目标会改变分配方案。

后两版七轮均值分别比 K30 高 **0.253% / 0.625%**。追加独立五轮后仍为正向，
但缩小为 **0.159% / 0.236%**：

| 独立五轮 | 平均 GFLOPS | 相对同轮 K30 | 同轮 strict 比例 |
|---|---:|---:|---:|
| strict | 21,495.7 | — | 100.00% |
| K30 | 20,730.2 | 基线 | 96.44% |
| 同 SASS control | 20,708.7 | −0.104% | 96.34% |
| 预算 235，实际 233 registers | 20,763.3 | +0.159% | 96.59% |
| 预算 240，实际 231 registers | 20,779.2 | +0.236% | 96.67% |

这些小信号值得保留，不能因为没有大幅提升就删除。但初轮冷缓存 profile 的 issue
没有随之提高，计时又存在 1935/1950 MHz 的频率变化，且同 SASS control 本身有
约 0.1% 的波动。因此目前不足以把它们宣布为满足全部接受指标的替代方案，更没有
依据把 96.67% 写成稳定达到 98%。独立轮次各自保留，不混合选择最高分。

K31 让下一步更明确：原组合的优势已经可重复，单纯减少寄存器、增加 stage 或
扩大 CTA 均不是免费收益。后续若继续投入，应围绕具体编译调度变化与资源约束
建立更窄的对照，并用同频率条件核实约 0.2% 的信号。默认 K10 和研究基线 K30
继续保留。完整正确性、工具检查、SASS/硬件指标及复现命令以
[K31 详细报告](18-K31-微内核精修与因果审计.md)和其中的版本化 CSV 为准。
