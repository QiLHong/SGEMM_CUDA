# RTX 3080 Kernel 10 调优记录

实验日期：2026-10-10（Asia/Shanghai）

GPU：NVIDIA GeForce RTX 3080（SM86，10 GB）

目标尺寸：`M=N=K=4096`，FP32，`alpha=0.5`，`beta=3.0`

## 结论先行

这份仓库里，RTX 3080 上实测最快的自写实现是 **Kernel 10（warp tiling）**，
不是编号更大的 Kernel 11/12。所有实现中最快的仍然是 Kernel 0 调用的 cuBLAS。

统一使用 4096³、预热 10 次和重复 50 次时，几个后期自写 kernel 的结果为：

| Kernel | 实现 | GFLOPS |
|---|---|---:|
| 9 | autotuned 2D tiling | 17,063.2 |
| **10** | **warp tiling** | **19,197.7** |
| 11 | double buffering | 17,252.8 |
| 12 | async-copy double buffering | 15,827.7 |

Kernel 11/12 的思路在理论上更先进，但当前具体实现付出了更多寄存器、共享内存和
同步成本。编号表示教学演进顺序，不是性能排名。最终 K10 每线程使用 184 个寄存器、
每 block 使用 16,640 B shared memory，且不发生 local-memory spill；K12 则使用 210 个
寄存器和 32,784 B shared memory。因此在这块 GPU 和这个矩阵尺寸上，K10 的计算、
访存与占用率组合更好。

## 怎样理解“106%”

原作者[文章](https://siboehm.com/articles/22/CUDA-MMM)和仓库表中，A6000 上的
Kernel 10 是 21,779.3 GFLOPS，cuBLAS 是 23,249.6 GFLOPS，即 **93.7%**，不是
106%。如果把两次不同机器、不同预热状态或不同轮次的数字交叉相除，就可能得到一个
超过 100% 的百分比，但它不能说明自写 kernel 超过了同机同口径 cuBLAS。

本报告把同一台 RTX 3080、同一构建、相同尺寸和预热方式下的 cuBLAS 定为 100%。
候选在计时前预热 10 次，并先通过仓库原有的 cuBLAS 数值正确性校验。

## 搜索过哪些参数

完整搜索了 24 组 tile，覆盖 `BK=8/16/32`、128/256 threads、方形与非方形
block tile，以及多种 warp tile、`WNITER`、`TM` 和 `TN`。加入最终的 padding 和
launch-bounds 配置后重跑，原 tile 仍以 19,615.2 GFLOPS 排名第一；第二名
`sub_8x4_n2` 为 19,534.9 GFLOPS。

最终 tile 是：

```text
BM=128, BN=128, BK=16
WM=64,  WN=64,  WNITER=4
TM=8,   TN=4,   threads=128
AS_PAD=4, MIN_BLOCKS=2
```

额外测试了 `--use_fast_math`、额外向量化选项、`maxrregcount`、L1/L2 cache load
修饰、shared-memory carveout 和交换 grid 轴，均未稳定胜过默认的 Release `-O3`。
256 线程配合 128×256 或 256×128 大 tile 会产生严重 spill，只剩约 0.6–0.9
TFLOPS，因此不能只看 tile 更大就认为会更快。

## 两个有效改动

### 1. A tile shared-memory padding

原布局把转置后的 A tile 存为 `As[BK][BM]`。在 `BM=128` 时，多个 lane 的写入会
映射到相同 bank。将 stride 改为 `BM+4` 后，Nsight Compute 指标如下：

| 指标（4096³） | `AS_PAD=0` | `AS_PAD=4` | 变化 |
|---|---:|---:|---:|
| Shared load bank conflicts | 0 | 0 | 不变 |
| Shared store bank conflicts | 50,331,648 | 16,777,216 | -66.7% |
| Shared store wavefronts | 83,886,080 | 50,331,648 | -40.0% |

`AS_PAD=1/2/3` 明显回退；4 和 12 的速度接近，所以选择额外 shared-memory 占用
更小的 4。安全的 `__restrict__` 别名提示也一并保留。

### 2. 两参数 `__launch_bounds__`

最终 kernel 使用 `__launch_bounds__(128, 2)`，告诉编译器每个 SM 至少需要容纳
两个 block。编译器因此可以把每线程寄存器数从 168 放宽到 184，减少指令与临时值
搬运；这虽然降低了理论 occupancy，却提高了实际吞吐。

交错三轮、每轮重复 50 次的结果：

| 配置 | 平均 GFLOPS | 寄存器/线程 | 结果 |
|---|---:|---:|---|
| 单参数 `launch_bounds(128)` | 19,058.3 | 168 | 基线 |
| `minBlocks=1` | 19,468.9 | 184 | 接近最优 |
| **`minBlocks=2`** | **19,446.6** | **184** | **采用；ptxas 资源目标** |
| `minBlocks=3` | 17,401.0 | 167 | 回退 |
| `minBlocks=4` | 734.8 | 128 | 816 B stack spill，淘汰 |

`minBlocks=1` 与 2 的细小差异属于运行波动；后续逐 tile 复核确认两者生成的 K10
SASS 完全相同，都是 184 registers、无 stack spill。第二个 launch-bounds 参数只是
ptxas 的资源分配目标，不保证运行时每个 SM 始终驻留相应数量的 block。相对原来的
单参数版本，受控三轮均值提升约 2.0%。新公平计时口径与完整瓶颈分析见 05 文档。

## 最终完整验证

清除所有 CMake 调参 cache 后，以源码默认参数重新构建。K10 在 128、256、512、
1024、2048、4096 六个仓库标准尺寸上全部通过原 runner 的 cuBLAS 正确性检查。

完整六尺寸运行中的 4096³ 结果：

| 实现 | GFLOPS | 相对同轮 cuBLAS |
|---|---:|---:|
| cuBLAS FP32 | 21,659.9 | 100.00% |
| 调优后 Kernel 10 | 19,560.0 | 90.31% |

两次额外独立长测分别为 19,475.0 和 19,475.4 GFLOPS；相同预热口径的 cuBLAS
为 21,612.1 GFLOPS，即约 90.11%。整轮搜索结束时的配对结果是 19,366.7 对
21,658.0 GFLOPS，即 89.42%。因此更诚实的跨轮范围是 **cuBLAS 的
89.4%–90.3%**，稳定中心约为 **90.1%**。

与加入 launch-bounds 前的受控均值 19,058.3 GFLOPS 相比，最终配置提升约 2.0%；
与上一版完整验证的 19,155.7 GFLOPS 相比提升约 2.1%。它已经是当前实现框架内、
本轮搜索得到的最好配置，但没有达到同口径 cuBLAS 的 106%。若要继续显著提升，需要
重写更有效的软件流水、做更细的 SASS 指令调度，或改走 Tensor Core；Tensor Core 会
改变精度/计算路径，不能直接作为本次普通 FP32 CUDA-core 结果的延续。

## 复现

```bash
MIN_BLOCKS=2 DEVICE=0 ./scripts/kernel_10_rtx3080_tuner.sh
```

脚本通过 CMake 编译期定义传参，不使用上游调优器的 `sed -i` 修改源码。搜索结束会
自动重建胜者并做 50 次长测。
