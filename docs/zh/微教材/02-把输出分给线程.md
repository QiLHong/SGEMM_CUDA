# 第 2 章 把输出分给线程

[上一章](01-从点积到内存地址.md) · [目录](README.md) · [下一章](03-访存与数据复用.md)

上一章有四个独立输出。现在的问题是：怎么告诉 GPU，“这个线程算这个位置”？
先把任务分清，再考虑怎样分得快。

## 1 从四个任务开始

把输出线性编号为 tid，使用 `row=tid/N, col=tid%N`。本例 N=2：

|tid|row|col|结果|
|---:|---:|---:|---:|
|0|0|0|58|
|1|0|1|64|
|2|1|0|139|
|3|1|1|154|

每个线程执行相同的乘加循环，只是 row/col 不同。这是 SIMT 入门最有用的直觉：
同一份程序，不同线程状态。真正硬件如何组织执行，不等于把 CPU 函数同时复制
无穷多份；后面还需要 warp、资源驻留和调度的概念。

## 2 三层软件分组与一层硬件资源

```text
一次 kernel launch
  → grid：一批 block
      → block：一组合作线程
          → thread：一个索引与私有状态

硬件 SM 接收可驻留的 block，按 warp 组织执行
```

在本项目目标架构上，一个 warp 是 32 个线程，lane 是其中编号。
一个 128-thread block 有四个 warp；一个 SM 可以驻留多个 block，但受资源限制。
不要把 block 当作 SM，也不要把 thread 当作永远独占一个 CUDA core。
基本定义见 [CUDA 线程层次](https://docs.nvidia.com/cuda/archive/12.4.1/cuda-c-programming-guide/index.html#thread-hierarchy)。

对一维 block：

```text
global_tid = blockIdx.x * blockDim.x + threadIdx.x
warp_in_block = threadIdx.x / 32
lane = threadIdx.x % 32
```

对于二维 block，先算 `tid=x+blockDim.x*y`。例如 blockDim=(16,16)，第一个 warp
覆盖两行各 16 个线程，而不是一整行 32 个 x。只说“二维 block 的一行是一个 warp”
是不可靠的，必须把尺寸代入。

## 3 把一个输出写成 CUDA 片段

下面只展示设备逻辑，M/N/K 为正，输入为有效非别名设备指针；没有包含主机分配、
拷贝和错误处理，不是本项目新增的可测优化版本。

```cpp
// 示意映射：x 方向覆盖列，y 方向覆盖行。
int row = blockIdx.y * blockDim.y + threadIdx.y;
int col = blockIdx.x * blockDim.x + threadIdx.x;
if (row < M && col < N) {
  float acc = 0.0f;
  for (int k = 0; k < K; ++k)
    acc += A[row*K+k] * B[k*N+col];
  C[row*N+col] = alpha*acc + beta*C[row*N+col];
}
```

与原 K1 的 x/y 选择不同，但数学可以相同。这体现一个重要原则：映射有设计自由，
必须同时检查输出是否完整、是否重复，以及同一 warp 的访存模式。

## 4 为什么需要边界检查

若 N=1000、每块列方向覆盖 32，最后一块会覆盖部分无效列。通常块数向上取整，
但向上取整只负责启动足够线程，不负责让无效线程的访存自动合法。

上面没有 barrier 的简单版本，可以让无效线程跳过计算。在合作加载 shared 的
版本里，则不能只照搬“越界就返回”：即使线程不写输出，也可能需要加载供别人
使用的数据或参与同步。第四章与第六章会重新处理这个问题。

## 5 哪些顺序不能假设

block 0 不保证先于 block 1 完成；一个 SM 上存在多个 warp，也不意味着它们在
同一时刻执行同一行源码。warp 内的分支也可能让有效线程分批执行。

因此，不应让一个普通 block 等待“稍后才可能被调度”的另一个 block 来解锁。
本项目把不同输出 tile 交给独立 block，跨 block 不做这样的生产消费依赖。
缓存局部性可以成为调优线索，但 block 编号不构成同步保证。

## 6 源码精读：先看谁 launch，再看设备端怎么算

工程里有两条入口，读代码前先区分：

```text
教学编号入口：sgemm.cu → src/runner.cu::run_kernel
                           → run_sgemm_naive / run_sgemm_coalesce → K1 / K2

研究审计入口：scripts/k32_audit.cu::main → launch lambda
                                          → runK30<Small,2> → sgemmK30
```

编号入口当前接到 K23；**不能把 K30 当作 `sgemm 30` 来运行**。
K30 使用独立 audit，命令在第七章。这是工程入口选择，不是算法差别。

### 6.1 同样 1,024 个线程，分工可以完全不同

[runner.cu](../../../src/runner.cu#L215) 中 K1 的实际启动配置是：

```cpp
dim3 gridDim(CEIL_DIV(M, 32), CEIL_DIV(N, 32));
dim3 blockDim(32, 32);
sgemm_naive<<<gridDim, blockDim>>>(M, N, K, alpha, A, B, beta, C);
```

`<<<...>>>` 中第一个参数是 block 数，第二个是每个 block 的线程布局，
不是矩阵的 M/N。代入 M=N=128：grid=(4,4)，每块 32×32=1,024 个线程。
K1 中 `x=blockIdx.x*32+threadIdx.x` 表示行，y 表示列。

K2 的启动把 block 改为一维 `32*32`，设备端使用：

```cpp
const int cRow = blockIdx.x * BLOCKSIZE + (threadIdx.x / BLOCKSIZE);
const int cCol = blockIdx.y * BLOCKSIZE + (threadIdx.x % BLOCKSIZE);
```

取同一 blockIdx=(1,2)，比较线性 tid=0、1、31、32：

|线性 tid|K1 的 threadIdx.x/y|K1 输出行/列|K2 输出行/列|
|---:|---|---|---|
|0|(0,0)|(32,64)|(32,64)|
|1|(1,0)|(33,64)|(32,65)|
|31|(31,0)|(63,64)|(32,95)|
|32|(0,1)|(32,65)|(33,64)|

两者都覆盖同一个 32×32 区域，但第一个 warp 的方向不同：K1 沿行走，
K2 沿列走。下一章的访存差异就来自这里，不是 K2 使用了更多线程。

### 6.2 不要把某个版本的 x/y 习惯套到所有版本

从 K4 开始，runner 改为 `grid.x` 对应输出列块、`grid.y` 对应行块。
K30 也是 `blockM=blockIdx.y*S::M`、`blockN=blockIdx.x*S::N`。
因此，看一个新 kernel 时应先抄下这两个公式，而不是默认 x 永远是行或永远是列。

K30 的 [runK30](../../../scripts/k32_audit.cu#L36) 启动配置有第三个参数：

```cpp
sgemmK30<S,Stages><<<dim3(n/S::N,(n+S::M-1)/S::M),S::Threads,shared>>>
    (n,n,n,alpha,a,b,beta,c);
```

这里 `shared` 是每个 block 请求的动态 shared **字节数**，不是线程数。
在 n=4096、S::M=S::N=128、S::Threads=128 时，共启动 32×32=1,024 个
block，每块四个 warp。它们并非同时全部驻留；硬件分批把 block 放到 SM。
本次调用的 131,072 个线程各负责 128 个输出，恰好覆盖 4096² 个元素。

动手核对：在仓库根目录执行下面的只读搜索，再对着 launch 和 kernel 两端画箭头。

```bash
rg -n 'run_kernel|run_sgemm_naive|run_sgemm_coalesce' src/runner.cu
rg -n 'blockM|blockN|FragmentIterator' src/kernels/30_kernel_mini_simt.cuh
```

## 7 练习

1. blockDim.x=128，blockIdx.x=3，threadIdx.x=70：全局编号、warp、lane 是多少？
2. blockDim=(16,16)，threadIdx=(3,1)：线性 tid、warp、lane 是多少？
3. 某 kernel 有 1,024 个输出，只启动 128 个线程，是否一定漏算？

### 参考答案

1. 全局编号 454，block 内 warp 2，lane 6，均从 0 开始。
2. tid=19，warp 0，lane 19。先线性化再分 warp。
3. 不一定。一个线程可循环处理多个输出，或者持有多个 accumulator。是否漏算
   取决于映射覆盖，不取决于输出数是否等于线程数。K30 就是每线程多个输出。
