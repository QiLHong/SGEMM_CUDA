# 第 7 章 验证与性能分析

[上一章](06-同步与双缓冲.md) · [目录](README.md) · [下一章](08-用K30串起整个项目.md)

到这里，你已经能提出一个改动。研究最重要的下一步不是马上宣布更快，而是建立
一个别人可以检查的比较：结果是否正确，测量是否公平，解释是否被证据支持。

## 1 先定义数值比较

本项目用 strict FP32 cuBLAS 作为参考，保持原 0.01 absolute error，并拒绝
非有限结果。严格 FP32 不是位级一致承诺：并行归约和浮点舍入顺序仍可导致差异。

简单理解舍入：机器只能表示有限集合中的数，实数运算的精确结果常需取近似。
`(a+b)+c` 与 `a+(b+c)` 可能经过不同的舍入过程。FMA 将乘加融合后舍入，
也可能不同于乘法先舍入、再加法。背景见
[NVIDIA 浮点说明](https://docs.nvidia.com/cuda/archive/12.4.1/floating-point/index.html)。

不要为了让新版 PASS 放宽门槛。当前输入集合通过，也不等于对极端尺度、强消去
或全部矩阵形状完成数值证明。生产使用需要扩大验证域。

## 2 beta 会改变重复测量的意义

若每次不恢复 C，beta=3 时执行的是递推 `C(t+1)=alpha*AB+3*C(t)`。
若每次恢复 C0，才是在重复相同输入。两种语义均可研究，但不能混成同一个结果。

公平入口采用后一种。C0 恢复 copy 放在计时区间外，因此报告的是 kernel-only
时间，不是包括初始化和数据传输的端到端时间。恢复动作也会影响缓存，所以所有
比较模式必须一致，不是把它忽略不提。

## 3 正确计时并检查错误

CPU 发出 kernel launch 通常不等设备完成就返回。要测设备执行，可以在同一流
中把 CUDA event 放在 kernel 前后，等待 stop 完成后获取时间。
只测 CPU launch 调用时间，会漏掉大部分设备工作。

还应检查启动错误与完成时的异步执行错误。预热让运行摆脱空闲初态，但不保证
温度/频率从此完全不变；记录状态并交错比较各模式，比先测完 A 再隔很久测 B 更可靠。

常用公式是：

```text
GFLOPS = 2*M*N*K / (time_ms*10^6)
相对 K10 提升 = K30_GFLOPS/K10_GFLOPS - 1
达到 cuBLAS 比例 = K30_GFLOPS/cuBLAS_GFLOPS
```

最后两个百分比不同，也都不是 GPU 理论峰值比例。只能用同批次的基线相除。

## 4 资源不是只有寄存器个数

编译器报告的寄存器、shared、stack 和 spill 决定了资源需求的一部分。
CUDA occupancy 查询估计最多能驻留多少 CTA；Nsight 的实测 occupancy 则反映
执行过程。二者均不等于“有多少 FP32 算力真正被使用”。

例如 K32 的两个版本分配 167 与 187 registers/thread，均无 spill，但五-warp
CTA 在 SM86 子分区的容量台阶不同，可驻留 CTA 从两个变成一个。
不能简单用总寄存器数除以线程数，更不能认为“没 spill 就资源充足”。
具体模型见[K32 报告](../19-K32-Warp角色分工与同步代价.md)。

## 5 从问题选择工具而不是堆指标

|问题|优先检查|不能直接推出的结论|
|---|---|---|
|数学结果是否可靠|数值对照与完整测试范围|少量 PASS 不证明全部输入|
|有没有非法访问或同步问题|Compute Sanitizer 与协议分析|工具 PASS 不代表更快|
|资源分配是否变化|ptxas、函数属性、occupancy 查询|较少寄存器不代表较短耗时|
|实际生成什么|PTX/SASS，必要时逐 PC 分析|源码 load 提前不保证机器码提前|
|有没有可发射工作|eligible、issue、stall|某个等待指标下降不等于吞吐提高|
|哪层存储服务变了|DRAM、L2、shared wavefront/conflict|缓存命中高不等于整体更好|

编译过程中 PTX 是虚拟指令层，SASS 用于观察目标 GPU 的最终指令。分析时要
区分静态数量和动态执行量：循环会重复指令，分支会跳过指令，谓词会改变有效线程。
例如静态 FFMA 翻倍，可能只是存在两条互斥路径，而不是数学工作量翻倍。

Nsight 会用 replay 等方式采集指标，缓存和时钟策略可能与常规 benchmark 不同。
因此不要拿 profiler duration 替代公平计时，也不要把所有 stall 数值当成可相加
的耗时百分比。定义参考 [Nsight Profiling Guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html)。

## 7 源码精读：一次 audit 从输入到 PASS 的全过程

本章固定读最新收尾入口 [scripts/k32_audit.cu](../../../scripts/k32_audit.cu)。
文件名有 K32，但其中的 `k30` 模式启动的是原 K30 V2；这样能在同一个二进制、
同一份测试逻辑里比较 K10/K30/cuBLAS。它不要求你先学习 K32 的 warp 分工。

先记住实际调用链：

```text
run_k32_audit.py 选择模式并检查资源门槛
  → run_k30_audit.py 安排尺寸、beta、轮次、测量顺序
      → audit mode size beta repeat warmup
          → 初始化 A/B/C0
          → strict reference 与 candidate 各运行一次
          → 逐元素校验
          → warmup 次预热
          → repeat 次 event 计时
          → RESULT 行
      → timing/fair.csv 或 tests/correctness.csv
  → summarize_k32_audit.py 检查完整性后生成报告 CSV
```

这几层名字相似，职责却不同。`.cu` 是一次进程内的设备实验；Python runner
组织多次实验；summarizer 不能替你补跑缺失的实验。

### 7.1 先读参数检查，不要先看 GFLOPS

[main 参数段](../../../scripts/k32_audit.cu#L62) 的参数顺序是：

```text
audit k30 4096 3 50 10
      模式 尺寸 beta repeat warmup
```

这里 M=N=K=size；alpha 在源码固定为 0.5。入口接受 128..4096 内的 128 倍数，
beta 只接受 0、1、3，repeat 至少为 1。自动正确性脚本从合法尺寸中选取
128/256/512/1024/2048/4096 六个，不是把所有合法尺寸都测了一遍。

当你声称“已通过全部测试”时，要说清是这个预定义测试集，而不是所有矩阵形状。
同理，这个入口不能直接拿来验证第一章的 2×3 小矩阵。

### 7.2 为什么需要五份设备矩阵

[初始化与分配段](../../../scripts/k32_audit.cu#L79) 使用：

|设备指针|含义|谁会修改它|
|---|---|---|
|da|输入 A|本实验中 kernel 只读|
|db|输入 B|本实验中 kernel 只读|
|di|不可变的初始 C0|初始化后保留，用作恢复源|
|dr|strict FP32 参考输出|cuBLAS|
|dc|候选 kernel 输出|所选模式|

`bytes=size_t(n)*n*sizeof(float)` 是一张矩阵的字节数。n=4096 时每张为
67,108,864 字节，即 64 MiB；五张设备矩阵合计 320 MiB，不包含库和其他开销。
`std::vector` 在这里保存主机数据，`cudaMalloc` 分配的是设备地址，两者不能混用。

initialize 分别用 index=0/1/2 初始化 A/B/C0，种子基值为 20261013。
输入是有限幅度、正负混合的离散值，不是覆盖全部 FP32 范围的随机数。
同一工具环境下各模式使用同样的生成过程；C 库 `rand()` 的序列并没有跨平台
一致性保证。严格跨机器重放还需要固定生成算法或保存输入及哈希。

### 7.3 strict cuBLAS 为什么把 db 放在 da 前面

[strict lambda](../../../scripts/k32_audit.cu#L89) 的关键调用是：

```cpp
BLAS_OK(cublasSetMathMode(handle, CUBLAS_PEDANTIC_MATH));
auto strict = [&](float *out) {
  BLAS_OK(cublasGemmEx(handle, CUBLAS_OP_N, CUBLAS_OP_N, n, n, n,
      &alpha, db, CUDA_R_32F, n, da, CUDA_R_32F, n, &beta,
      out, CUDA_R_32F, n, CUBLAS_COMPUTE_32F_PEDANTIC, CUBLAS_GEMM_DEFAULT));
};
```

传统 cuBLAS 接口按列主序解释矩阵。行主序 C=AB 的同一内存按列主序看是 Cᵀ，
于是调用计算 BᵀAᵀ：B 的指针在前、A 在后，不需要做一次真正的转置拷贝。
这里都是方阵 n，若扩展到矩形，维度和 leading dimension 必须重新逐项推导。

`CUDA_R_32F` 说明存储类型；`CUBLAS_COMPUTE_32F_PEDANTIC` 与 math mode
限定计算策略。不能只看到输入为 float 就宣布“与任意 cuBLAS FP32 调用同口径”。
脚本还会移除 NVIDIA_TF32_OVERRIDE 环境变量，直接运行时使用 `env -u`。
语义见 [cuBLAS 12.4 compute type](https://docs.nvidia.com/cuda/archive/12.4.1/cublas/index.html#cublascomputetype-t)。

这些 API 设置是配置证据，实际执行路径仍应由当次 Nsight/SASS 核实。
历史记录发现 SIMT kernel，不保证任何新 GPU、形状或库版本都选择同一 kernel。

### 7.4 数值验证到底验证了哪一次输出

[校验段](../../../scripts/k32_audit.cu#L108) 先做：

```cpp
CUDA_OK(cudaMemcpy(dr, di, bytes, cudaMemcpyDeviceToDevice)); strict(dr);
CUDA_OK(cudaMemcpy(dc, di, bytes, cudaMemcpyDeviceToDevice)); launch();
CUDA_OK(cudaDeviceSynchronize());
```

参考和候选都从相同 C0 开始。完成后各自拷回主机，逐元素执行：

```cpp
double e = std::abs(double(actual[i]) - expected[i]);
if (!std::isfinite(e) || e > 0.01) {
  // 原程序输出 FAIL 并返回非零。
}
```

转换为 double 是为了计算两个已得到的 FP32 结果之间的误差，不是把 GPU
乘法改成 FP64。非有限检查很重要：仅用 `NaN > 0.01` 判断并不能可靠拒绝 NaN。

这里有一个必须记住的边界：**逐元素比较只发生在预热和计时之前的这一次 launch**。
计时循环检查 CUDA 错误，但没有每轮都把 C 拷回重比。RESULT 的 max_error/PASS
来自前面的数值检查，不能讲成“50 次计时结果都逐元素验证过”。

### 7.5 启动检查、完成检查、Sanitizer 各负责什么

launch lambda 末尾有 `cudaGetLastError()`，用于检查启动相关错误；后面的
device/event synchronization 等操作检查异步执行完成时报告的错误。
两者不能代替对合法但错误结果的数值检查，也不能覆盖所有竞态。

因此三个检查层次都需要：

- 数值对照：是否算成了预期矩阵，误差是否达标。
- CUDA 返回值检查：调用和执行是否报告失败。
- Compute Sanitizer：检查非法访存、shared race、同步使用等指定类别的问题。

例如把 A 的合法行读错，可能只有数值检查失败；某次 race 恰好没改变结果，
数值检查也可能 PASS。它们互补，不是重复劳动。

## 8 源码精读：哪些时间进入最终 GFLOPS

[预热和计时段](../../../scripts/k32_audit.cu#L122) 可以分为三个区域：

```text
区域 A：恢复 C0 → launch，重复 warmup 次 → 同步

区域 B（每次 repeat）：
  恢复 C0                 不在 event 区间
  NVTX push measure
  event start
  launch                  纳入 event 测量
  event stop
  NVTX pop
  等待 stop → 读取 elapsed

区域 C：求平均、输出 RESULT、释放资源
```

实际内层代码如下：

```cpp
CUDA_OK(cudaMemcpy(dc, di, bytes, cudaMemcpyDeviceToDevice));
nvtxRangePushA("measure");
CUDA_OK(cudaEventRecord(start)); launch(); CUDA_OK(cudaEventRecord(stop));
nvtxRangePop();
CUDA_OK(cudaEventSynchronize(stop));
float ms; CUDA_OK(cudaEventElapsedTime(&ms,start,stop)); total += ms;
```

NVTX 是给 profiler 识别测量 launch 的标记，不是另一个时间计算公式。
这里没有显式创建其他 stream，设备工作与 events 使用当前默认流的顺序。
这种计时通常称为 kernel-only，但其精确定义是两 event 间的设备时间，
不是整个程序耗时，也不是纯 FFMA 指令时间。

### 8.1 为什么 beta=3 不会在这里越测越大

因为每次 launch 前都恢复 dc=di，测的是相同的
`C=0.5*AB+3*C0`。若没有恢复，第 t 次会把第 t−1 次输出再乘 3，既改变输入，
也可能逐渐产生巨大数值。本工程的历史 legacy benchmark 保留另一种语义，
请在 [sgemm.cu](../../../sgemm.cu) 搜索 reset/fair/legacy 分支，不要混用两类数据。

恢复操作虽然未计时，仍可能改变缓存状态。这不是错误，而是需要所有模式一致
执行、并明确报告的实验条件。也因此，测量结果不能直接解释为端到端应用加速。

### 8.2 repeat 与 round 不是同一个数

一次 audit 进程中 repeat=50，输出的是 50 次 event 耗时的平均值；这叫一条
轮内结果。Python runner 再把不同模式交错执行多轮，才得到跨轮波动。

[run_k30_audit.py](../../../scripts/run_k30_audit.py#L42) 的 fair 配置是
4096³、beta=3、repeat=50、warmup=10，前面还单独用 K10 热身。
模式顺序用 `MODES[(i+r)%len(MODES)]` 循环移位，**不是随机抽样**。
只比较 strict/k10/k30 时，三轮顺序为：

```text
第 1 轮：strict → k10 → k30
第 2 轮：k10 → k30 → strict
第 3 轮：k30 → strict → k10
```

六轮则每个位置出现两次。这帮助减轻顺序偏差，但不能消除其他进程干扰或长期
温漂。runner 记录的 GPU 温度/时钟只是各进程前后的快照，不是整个时间段的连续采样。

## 9 跟着工程跑：分清小练习与完整复现

下面是**供读者在目标 CUDA 环境执行的命令**，不是这次教材修改的新测量结果。
使用仓库根目录与同一个 shell；OUT 必须尚不存在，重复时换一个 session 名。
先保证 GPU 无并发计算任务，不要并行执行 benchmark 与 profiler。

### 9.1 构建并读资源，不急着跑 4096

```bash
OUT=benchmark_results/microbook-codewalk-session1
bash scripts/build_k32_audit.sh "$OUT"
python3 scripts/analyze_k32_binary.py "$OUT"
python3 scripts/run_k32_audit.py resources --directory "$OUT"
env -u NVIDIA_TF32_OVERRIDE "$OUT/audit" k30 128 3 1 0
```

逐步解释：

1. [build_k32_audit.sh](../../../scripts/build_k32_audit.sh) 使用
   `-O3 -DNDEBUG -std=c++17 -arch=sm_86 -lineinfo -DSGEMM_K10_MIN_BLOCKS=2 -Xptxas=-v`，
   编译日志写到 OUT/build.log；K10 与研究版本在同一次构建中。
2. [analyze_k32_binary.py](../../../scripts/analyze_k32_binary.py) 解析 ptxas 并反汇编，
   生成 resources.csv、static-sass.csv、schedule.csv、sass_*.txt。
   这是二进制静态分析，不产生 GFLOPS。
3. resources 动作实际查询函数属性与 occupancy 上限，生成 runtime-resources.csv。
4. 最后一条才启动一次小尺寸 K30 检查。四个动作都成功，仍不等于完整验证。

当前资源 gate 是 **不超过 240 registers/thread 且 spill load/store 均为零**，
这是收尾脚本针对这些版本的规则，不是早期 K19/K20 的 200/220 上限，
更不是硬件普适最佳值。K30 的 235 不应被旧实验门槛误判。

还要区分 static/dynamic shared：runtime-resources 的 dynamic_shared_bytes
在 K10 上为 0，不表示 K10 没用 shared；它使用静态声明。
总量、用户请求量和 profiler 分配口径必须分别看列名与来源。

### 9.2 只学习 K10/K30 的最小研究集

```bash
python3 scripts/run_k32_audit.py correctness --directory "$OUT" --modes k10 k30
python3 scripts/run_k32_audit.py memcheck --directory "$OUT" --modes k30
python3 scripts/run_k32_audit.py sync --directory "$OUT" --modes k30
python3 scripts/run_k32_audit.py fair --directory "$OUT" --modes strict k10 k30 --rounds 6
```

预期覆盖是两个候选 × 六尺寸 × 三个 beta=36 条数值测试。
这里 Sanitizer 只选 K30：memcheck 为 128/256/4096；racecheck 和 synccheck
各为 128/256，beta=3，共七次。脚本本身跳过 strict 和 K10 的 Sanitizer，
所以不能声称这组命令对所有模式、所有尺寸都跑了全部工具。

这个子集适合学习，但**不能直接交给全量 summarize_k32_audit.py 当完整实验发布**。
全量汇总会要求编译通过的全部模式、指定 profile 和 Sanitizer；缺失时拒绝是正确的。
要正式复现收尾报告，请另开新目录，执行[完整复现手册](../20-项目复现与简历讲述.md)
中的全量命令，避免在同一输出位置重复写同名日志。

## 10 从 CSV 与 SASS 得出一个有边界的结论

### 10.1 先分清统计对象

一次 RESULT 的 ms 是 repeat 次平均耗时；gflops 用这个平均耗时换算。
fair.csv 的一行对应一个模式的一轮，不是一条单 launch 样本。
[汇总函数 performance](../../../scripts/summarize_k32_audit.py#L52) 再计算：

|列|含义|
|---|---|
|mean_gflops|各轮 GFLOPS 的算术平均|
|min_gflops/max_gflops|各轮均值的范围，不是 50 次单 launch 的极值|
|stdev_gflops|这些轮均值的样本标准差，不是置信区间|
|pct_strict|本模式 mean_gflops / strict mean_gflops ×100|
|gain_vs_k30_pct|本模式均值相对 K30 均值的提升百分比|
|paired_gain_min/max_pct|每轮对同轮 K30 做比值后的最小/最大提升|

“均值的比值”与“每轮比值的均值”不是同一统计量；不要不加说明地替换。
又因为倒数是非线性的，平均 GFLOPS 不一定恰好等于用跨轮平均 ms 换算的 GFLOPS。
如果收益很小，应看配对方向、波动及独立确认，不能只看小数点后的最高分。

### 10.2 先提出问题，再打开对应指标

下面是仓库采集/汇总实际使用的部分字段；单位与完整指标名应回到
[runner metrics](../../../scripts/run_k30_audit.py#L87) 核对：

|报告列|本项目追问|必须避免的误读|
|---|---|---|
|issue_pct|调度器是否更经常发射指令|不等于 FP32 指令占比|
|no_issue_pct|多少相应周期没有发射指令|不能直接改名为 no eligible warp|
|eligible_warps|每调度器有多少可发射 warp|不等于活跃或驻留 warp 总数|
|fp32_pct|FMA pipe 活跃情况是否改善|不是严格的理论峰值 GFLOPS 百分比|
|shared_load_wavefronts|shared 装载需要多少服务工作|不全是 bank conflict|
|shared_load_conflicts|额外冲突是否发生|为零仍可能有基础服务成本|
|local_load/store_sectors|执行时有无 local 流量|与 ptxas spill 字节不是同单位|
|long/short_scoreboard|依赖等待形态是否改变|不能单项换算为可回收毫秒数|

特别是 no_issue 与 no eligible：有可发射 warp 也可能没有成功发射，两个事件
不等价。复制一列表格到报告前，先知道计数器的事件和归一化口径。

### 10.3 同一次性能比较不能混用 cold 与 steady

```bash
python3 scripts/run_k32_audit.py profile --directory "$OUT" --modes strict k10 k30
python3 scripts/run_k32_audit.py profile --directory "$OUT" --modes strict k10 k30 --policies steady
python3 scripts/run_k32_audit.py source --directory "$OUT" --modes strict k10 k30
```

默认 cold 使用 kernel replay、cache-control=all、clock-control=base；
steady 使用 application replay、cache-control=none、clock-control=none。
脚本用 NVTX measure/ 过滤并采集一个测量 launch，避免把数值校验或预热错当成目标。
同一策略内比较模式；常规 CUDA event 吞吐另外成表。

### 10.4 SASS 应怎样和源码交叉阅读

先在 sass_k30.txt 找主循环的回跳与 FFMA/LDS/LDG/STS/BAR，再对照第六章的
load→compute→store→barrier。不要逐条机器指令硬套一行 C++：展开、调度和
寄存器重用都可能改变顺序。

static-sass.csv 统计整个函数的静态指令数量；schedule.csv 的 linear_ffma_before
是线性地址窗口中的 FFMA 数，不是考虑所有分支后的动态距离。
库 kernel 的 SASS 则要从 Nsight 捕获的路径读取，不能指望仅对自己的可执行文件
做 cuobjdump 就得到所调用 cuBLAS 库内部的全部机器码。

一个合格的小结应分三句写：

1. **测量**：同一批交错结果是否稳定更快，幅度与波动是什么。
2. **解释**：哪些资源/指令/硬件计数变化支持这个现象。
3. **边界**：哪些因果仍未隔离，哪些尺寸、输入或环境没有验证。

第八章会用仓库已经保存的真实 K30 数据做这件事。本章命令不构成新的 PASS
或性能记录，学习者运行后应保留自己的完整日志，而不是复制教材里的历史数字。

## 11 练习

1. 1024³ SGEMM 耗时 1 ms，GFLOPS 是多少？
2. 新版某一轮最高分比基线高，但多轮均值持平，可以接受吗？
3. 有人说“long-scoreboard 降了 50%，因此 kernel 时间一定也减少 50%”，错在哪里？

### 参考答案

1. 2147.483648 GFLOPS，约 2.147 TFLOPS。
2. 不能据单次峰值宣布稳定收益。应看配对轮次、波动与独立确认，并保持其他条件一致。
3. stall counter 的单位和归一化不一定是时间占比；不同等待可能重叠或转移，
   新实现也可能增加其他成本。性能要测量，不能把一个计数器按比例换算成总时间。
