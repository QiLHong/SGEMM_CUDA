# 第 7 章 验证与性能分析

[上一章](06-同步与双缓冲.md) · [目录](README.md) · [下一章](08-用K30串起整个项目.md)

到这里，你已经能提出一个改动。研究最重要的下一步不是马上宣布更快，而是建立
一个别人可以检查的比较：结果是否正确，测量是否公平，解释是否被证据支持。

## 1 先定义数值比较

本项目用 strict FP32 cuBLAS 作为参考，保持原 0.01 absolute error，并拒绝
非有限结果。严格 FP32 不是位级一致承诺：并行归约和浮点舍入顺序仍可导致差异。

简单理解舍入：机器只能表示有限集合中的数，实数运算的精确结果常需取近似。
`(a+b)+c` 与 `a+(b+c)` 可能经过不同的舍入过程。FMA 将乘加融合后舍入，
也可能不同于乘法先舍入、再加法。背景见
[NVIDIA 浮点说明](https://docs.nvidia.com/cuda/archive/12.4.1/floating-point/index.html)。

不要为了让新版 PASS 放宽门槛。当前输入集合通过，也不等于对极端尺度、强消去
或全部矩阵形状完成数值证明。生产使用需要扩大验证域。

## 2 beta 会改变重复测量的意义

若每次不恢复 C，beta=3 时执行的是递推 `C(t+1)=alpha*AB+3*C(t)`。
若每次恢复 C0，才是在重复相同输入。两种语义均可研究，但不能混成同一个结果。

公平入口采用后一种。C0 恢复 copy 放在计时区间外，因此报告的是 kernel-only
时间，不是包括初始化和数据传输的端到端时间。恢复动作也会影响缓存，所以所有
比较模式必须一致，不是把它忽略不提。

## 3 正确计时并检查错误

CPU 发出 kernel launch 通常不等设备完成就返回。要测设备执行，可以在同一流
中把 CUDA event 放在 kernel 前后，等待 stop 完成后获取时间。
只测 CPU launch 调用时间，会漏掉大部分设备工作。

还应检查启动错误与完成时的异步执行错误。预热让运行摆脱空闲初态，但不保证
温度/频率从此完全不变；记录状态并交错比较各模式，比先测完 A 再隔很久测 B 更可靠。

常用公式是：

```text
GFLOPS = 2*M*N*K / (time_ms*10^6)
相对 K10 提升 = K30_GFLOPS/K10_GFLOPS - 1
达到 cuBLAS 比例 = K30_GFLOPS/cuBLAS_GFLOPS
```

最后两个百分比不同，也都不是 GPU 理论峰值比例。只能用同批次的基线相除。

## 4 资源不是只有寄存器个数

编译器报告的寄存器、shared、stack 和 spill 决定了资源需求的一部分。
CUDA occupancy 查询估计最多能驻留多少 CTA；Nsight 的实测 occupancy 则反映
执行过程。二者均不等于“有多少 FP32 算力真正被使用”。

例如 K32 的两个版本分配 167 与 187 registers/thread，均无 spill，但五-warp
CTA 在 SM86 子分区的容量台阶不同，可驻留 CTA 从两个变成一个。
不能简单用总寄存器数除以线程数，更不能认为“没 spill 就资源充足”。
具体模型见[K32 报告](../19-K32-Warp角色分工与同步代价.md)。

## 5 从问题选择工具而不是堆指标

|问题|优先检查|不能直接推出的结论|
|---|---|---|
|数学结果是否可靠|数值对照与完整测试范围|少量 PASS 不证明全部输入|
|有没有非法访问或同步问题|Compute Sanitizer 与协议分析|工具 PASS 不代表更快|
|资源分配是否变化|ptxas、函数属性、occupancy 查询|较少寄存器不代表较短耗时|
|实际生成什么|PTX/SASS，必要时逐 PC 分析|源码 load 提前不保证机器码提前|
|有没有可发射工作|eligible、issue、stall|某个等待指标下降不等于吞吐提高|
|哪层存储服务变了|DRAM、L2、shared wavefront/conflict|缓存命中高不等于整体更好|

编译过程中 PTX 是虚拟指令层，SASS 用于观察目标 GPU 的最终指令。分析时要
区分静态数量和动态执行量：循环会重复指令，分支会跳过指令，谓词会改变有效线程。
例如静态 FFMA 翻倍，可能只是存在两条互斥路径，而不是数学工作量翻倍。

Nsight 会用 replay 等方式采集指标，缓存和时钟策略可能与常规 benchmark 不同。
因此不要拿 profiler duration 替代公平计时，也不要把所有 stall 数值当成可相加
的耗时百分比。定义参考 [Nsight Profiling Guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html)。

## 6 实践分成离线和硬件两条路

不使用 GPU，也能先运行本书练习、查看 CSV 并手算比例：

```bash
python3 scripts/check_microbook_examples.py
python3 scripts/verify_zh_translation.py
```

有相应 GPU 时，完整验证按[复现手册](../20-项目复现与简历讲述.md)执行。
最小构建与冒烟入口如下，使用全新目录，不覆盖历史：

```bash
OUT=benchmark_results/microbook-smoke-session1
bash scripts/build_k32_audit.sh "$OUT"
python3 scripts/analyze_k32_binary.py "$OUT"
env -u NVIDIA_TF32_OVERRIDE "$OUT/audit" k30 128 3 1 0
```

这只检查一次小规模运行，不能据此声称完成六尺寸验证或复现 20.8 TFLOPS。
实际吞吐使用固定输入、多轮交错及同轮 strict 基线；大型 profiler 采集不要与
其他 GPU 工作并发。本教材没有为出版重新启动这些实验。

## 7 练习

1. 1024³ SGEMM 耗时 1 ms，GFLOPS 是多少？
2. 新版某一轮最高分比基线高，但多轮均值持平，可以接受吗？
3. 有人说“long-scoreboard 降了 50%，因此 kernel 时间一定也减少 50%”，错在哪里？

### 参考答案

1. 2147.483648 GFLOPS，约 2.147 TFLOPS。
2. 不能据单次峰值宣布稳定收益。应看配对轮次、波动与独立确认，并保持其他条件一致。
3. stall counter 的单位和归一化不一定是时间占比；不同等待可能重叠或转移，
   新实现也可能增加其他成本。性能要测量，不能把一个计数器按比例换算成总时间。
