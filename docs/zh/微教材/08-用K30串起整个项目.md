# 第 8 章 用 K30 串起整个项目

[上一章](07-验证与性能分析.md) · [目录](README.md)

前七章不是孤立知识点。现在把它们变成一条研究链：从地址到复用，从映射到同步，
从机器码到测量，最后决定一个方案是否值得保留。

## 1 起点不是慢速 naive 而是已经很好的 K10

K10 已有合并搬运、shared 缓存、warp tiling 和寄存器外积。本机调优后在
4096³ strict FP32 下约为同口径 cuBLAS 的 91%。因此继续加一个“常用技巧”，
往往只是改变资源分布，不再像从 naive 到 shared 那样容易获得大幅收益。

K15 的 grid 重排、K16 的 XOR、K17 的 B-only async、K18 的简单 fragment
变化、K19 的预取都没有产生稳定替代方案。它们不是白做：每个实验都在收紧
假设。但结论只限于被测试的实现，不能宣布整个方向在所有设计中永远无效。

## 2 关键转折是把 shared 服务量和同步放在一起

K30 采用独立分层 skeleton，保留 128×128 CTA 和 BK16，重新组织每 lane 的
输出与 fragment 消费。第五章已经推导：从 K10 的 A8/B16 改为 A16/B8，并不是
增加每个线程的输出数，而是改变谁在同一条 warp 指令中读取哪些数据。

主循环动态 LDS 数量相同，wavefront 从约 335.54 M 减到 201.33 M，约少 40%。
但单阶段 V1 性能仍然下降，说明这一项不能独立解释突破。

V2 再使用两个 shared slot 与单次轮末 barrier，让“发布 future”和“退休 current”
在一个正确协议中完成。动态 BAR 接近减半。测得 issue 和 FP32 active 同时提升，
零 spill，235 registers/thread。这才形成了可接受的组合。

## 3 用同一批 CSV 计算成果

下面取自[K30 原七轮统计](../../results/k30-20261013/performance.csv)，不是本书新跑的结果：

|实现|平均 GFLOPS|应怎样解释|
|---|---:|---|
|strict FP32 cuBLAS|21592.73|同一批参考|
|K10|19652.21|已经调优的稳定对照|
|K30 V1 单阶段|18575.74|shared 指标更好，但整体回退|
|K30 V2 双阶段|20801.16|当前最佳研究版本|
|K30 V3 四阶段|15705.58|更多 stage 带来资源代价|

代入第七章公式，V2 相对 K10 提升约 5.85%，达到 strict 的 96.33%。
独立三轮确认仍约 +5.62%、96.25%。这比挑选一轮最高分更有说服力。
不同批次的绝对 GFLOPS 不直接拼接；后续复测比例略有变化，不是 K30 又改快了。

## 4 哪些好听的解释必须拒绝

第一种是“单独的新 layout 带来了全部收益”。V1 反例不支持这种说法。
第二种是“源码预取完美隐藏了 global latency”。SASS 将 LDG 下沉到主循环
2,046 条 FFMA 之后，也不支持这种说法。
第三种是“相同 occupancy 就相同性能”。K10/K30 的 issue 和 shared 服务量
不同，已经给出反例。

严谨的解释不是越复杂越好，而是没有超过证据：新的 fragment 服务方式与
双槽同步组织共同形成净收益，尚未把每项贡献精确拆成可相加的百分比。

## 5 为什么没有停留在成功叙事

K31 继续测试资源预算、装载时机、stage 和 CTA 扩展，没有稳定胜出。
K32 则用一个 producer warp 加四个计算 warp，验证搬运与计算分工。

在[K32 最终六轮](../../results/k32-20261013-final/performance.csv)里，K30 为
20851.74，K32 overlap 为 20842.38 GFLOPS，相差约 −0.045%，按持平处理。
long-scoreboard 明显下降，却没有更高吞吐。这告诉我们，一项等待指标改善
可能伴随交接和其他执行成本，不能只追一个 counter。

删除额外 barrier 的版本又出现寄存器 167→187、驻留 CTA 两个→一个、吞吐
明显回退。后续静态追踪定位到尾部 accumulator 重命名，计算数据的同时存活
峰值只增加 4，物理分配却增加 20。不能直接说“算法多需要 20 个寄存器”，
也还没完全解释 ptxas 的分配决策。

这些反例帮助我们在合理位置停下来：保留 K30，暂停继续堆叠技巧。

## 6 从教材走向面试和工程

面试时可以用四句话组织，而不是报一串 kernel 编号：

1. **问题**：已调优的 SIMT SGEMM 与严格 FP32 cuBLAS 仍有差距。
2. **方法**：统一测试口径，再分析 shared 服务量、同步协议和最终机器码。
3. **结果**：K30 的组合设计在 RTX 3080、4096³ 达到约 20.8 TFLOPS、96.3% 同口径 cuBLAS。
4. **边界**：没有替代生产矩阵库，没有精确归因全部剩余差距，也没有把失败实验隐藏。

如果要进入工程应用，还要定义真实 shape、矩形/tail、stride、batch、别名与
数值范围，再建立更广的测试和 dispatch 策略。本项目的固定形状成绩不能直接
换算成某个模型推理加速百分比。

## 7 工程串读：一张“证据账本”比一句优化总结更有用

现在尝试不按章节读，而是围绕一个结论穿过整个仓库。

|想说的结论|先读实现|再读证据|最多能说到哪里|
|---|---|---|---|
|每 lane 仍有 128 个输出|K30 Shape / FragmentIterator|CPU 输出覆盖测试、lane-mapping.csv|坐标覆盖成立，不代替 GPU 数值验证|
|双槽减少同步需求|sgemmK30 的 STAGES 分支|动态 BAR、协议检查、Sanitizer|被测试协议安全，同步组织不同|
|shared 服务量减少|WarpIteratorA/B / compute|mainloop-lds.csv、nsight.csv|服务工作下降，不直接等于总耗时下降|
|没有 spill|源码数组不能单独证明|ptxas、resources.csv、local 指标|该二进制/路径的证据，换编译器要重查|
|比 K10 快约 5.85%|相同 audit launch 与计时逻辑|同批 fair.csv、performance.csv|RTX 3080 / 4096³ / 指定口径，不是所有 GEMM|
|大幅隐藏了 global latency|next.load 在源码的位置|SASS 的实际 LDG 位置|现有证据不支持这句话|

这里的结果文件均在 [K30 历史归档](../../results/k30-20261013/)，
代码为 [30_kernel_mini_simt.cuh](../../../src/kernels/30_kernel_mini_simt.cuh)，
CPU 模型为 [check_microbook_examples.py](../../../scripts/check_microbook_examples.py)。
最好能指着文件解释，而不是只记住术语。

### 7.1 用同策略硬件数据练习推理

下面取 [nsight.csv](../../results/k30-20261013/nsight.csv) 的 **cold** 行，
为了阅读做了取整。wavefront 是整核汇总，不是只截主循环；不要与原始数值要求
完全相等的主循环表混用。

|指标|K10|K30 V1|K30 V2|
|---|---:|---:|---:|
|registers/thread|184|199|235|
|实测 occupancy|16.60%|16.54%|16.54%|
|issue_pct|79.16%|73.08%|83.30%|
|fp32_pct|73.71%|68.34%|77.49%|
|shared-load wavefront|335.55 M|201.33 M|201.35 M|
|shared-load conflicts|0|0|22,480|

先看 V1：wavefront 大幅减少，但 issue、FP32 与吞吐一起下降，所以“shared
服务量降低”不构成单独成功。再看 V2：occupancy 与 V1 接近，却恢复并超过 K10
的 issue/FP32；两槽同步组织与新 fragment 映射的组合才形成净收益。

也不要隐藏 V2 的非零 conflict：这批整核采集有少量 shared-load conflicts，
不能把 K10 的零冲突口号复制给所有版本。零冲突不是唯一目标，总服务量、等待、
资源和最终吞吐需要合看。

这些关联仍不是各项收益的精确分解。要说“barrier 节省了 X%、layout 节省了 Y%”，
还需要能隔离变量的实验，而不是把计数器百分比相加。

### 7.2 不开 GPU，亲手从历史 CSV 算出简历数字

在仓库根目录运行这段只读代码，它不生成或覆盖任何结果：

```bash
python3 - <<'PY'
import csv
from pathlib import Path

p = Path('docs/results/k30-20261013/performance.csv')
with p.open() as f:
    rows = {r['mode']: r for r in csv.DictReader(f)}
k10, k30, strict = [float(rows[m]['mean_gflops']) for m in ('k10', 'v2', 'strict')]
print(f'K30: {k30 / 1000:.3f} TFLOPS')
print(f'vs K10: {100 * (k30 / k10 - 1):+.2f}%')
print(f'of strict cuBLAS: {100 * k30 / strict:.2f}%')
PY
```

输出应是约 20.801 TFLOPS、+5.85%、96.33%。这三个数来自同一批数据，
不是从不同报告挑出最好的一对。原 K30 实验把双阶段称为 `v2`；收尾 k32_audit
把相同实现称为 `k30`，查表时要先确认 mode 的含义。

下一步打开 fair.csv，检查 v2 是否确有七行，再检查对应轮的 strict/k10。
然后读 confirm-performance.csv，确认独立批次是否支持同方向结论。
仅重新计算历史 CSV 不等于在当前机器重现了 GPU 吞吐。

### 7.3 把故事讲成“我怎样知道”，而不只是“我做了什么”

可以这样复述整个工程：

> 我先用 K1/K2 理解输出分工如何影响跨 lane 访存，再用 K3/K5 建立合作加载和
> 寄存器外积模型。到 K10 后，继续加局部技巧没有稳定收益，于是把研究重点转到
> ownership、shared 消费和同步协议的组合。K30 的单阶段反例帮助我确认：
> 不能只凭 wavefront 改善宣布成功。双阶段版本经过统一 FP32 校验、交错计时、
> 资源与机器码核对，才保留为最佳研究基线。后续分工实验虽然改善了某类等待，
> 吞吐却持平，因此我选择停止，而不是继续堆复杂度。

这段是表达示例，面试时应按你实际理解和参与的部分诚实讲述，并能现场推导
第五章的一个 lane 和第六章的一轮协议。使用 AI 辅助并不妨碍学习，但不能把
尚未理解的生成代码或报告当成自己已掌握的设计经验。

## 8 毕业练习

1. 不看第五章，画出 warp 0、lane 0 在 K10 和 K30 中的输出集合，说明相同点与不同点。
2. 面试官说“零 bank conflict，所以 shared 不可能是优化方向”，你怎样用本项目反驳？
3. 用两分钟解释 K30 的成功，再主动讲一个它没有证明的结论。

### 参考答案与评分要点

1. K10 为 M 0..7、N 四组间隔 16 的四列；K30 为 M 四组间隔 16 的四行、N 两组
   间隔 32 的四列。两者都是 128 个输出，但跨 lane 的消费关系不同。
2. conflict 与基础 wavefront 服务量不是同一指标；K30 降低了服务量。但还需
   补充 V1 没有加速，避免从一个错误的绝对结论跳到另一个。
3. 合格回答应出现公平 FP32 基线、ownership 与同步的组合、独立确认，并承认
   没有证明大范围 global/compute overlap 或精确分解剩余差距。只报 96.3% 不够。
