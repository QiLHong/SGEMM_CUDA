# 第 1 章 从点积到内存地址

[目录](README.md) · [下一章](02-把输出分给线程.md)

本章只解决一件事：在讨论 GPU 之前，准确说出一个输出需要哪些输入，以及这些
输入在内存的哪里。性能优化不能修复错误的数学或地址。

## 1 一个贯穿入门的小例子

先令 alpha=1、beta=0，计算下面两个矩阵的乘积。

```text
A = [1 2 3]       B = [ 7  8]
    [4 5 6]           [ 9 10]
                     [11 12]

A: 2×3           B: 3×2           C: 2×2
```

取 A 的第 0 行和 B 的第 0 列，对应相乘再相加：

```text
C[0,0] = 1*7 + 2*9 + 3*11 = 58
C[0,1] = 1*8 + 2*10 + 3*12 = 64
C[1,0] = 4*7 + 5*9 + 6*11 = 139
C[1,1] = 4*8 + 5*10 + 6*12 = 154
```

这里 M=2、N=2、K=3。M/N 决定有多少个输出，K 决定一个输出要累加多长。
四个输出可以独立计算；同一个输出内部的三项乘积需要合成一个结果。
这两个性质分别解释了为什么可以并行、为什么要有 accumulator。

## 2 三重循环并不神秘

下面是逻辑伪代码，不涉及 GPU 调度：

```text
for row in 0..M-1:
    for col in 0..N-1:
        acc = 0
        for k in 0..K-1:
            acc += A[row,k] * B[k,col]
        C[row,col] = acc
```

accumulator 就是 acc：它保留已经累加的部分结果。我们可以把 row/col 的不同
组合交给不同线程，但每个线程仍要知道自己在更新哪个 acc。
后面的高级 kernel 依然在做这件事，只是一个线程不再只拿一个 acc。

如果有 alpha/beta，最后一行应是 `C=alpha*acc+beta*old_C`。
例如旧 C 全为 1、alpha=0.5、beta=3，本例输出成为：

```text
[32    35]
[72.5  80]
```

不要在每个 k 都把 beta*old_C 加一遍；旧 C 的处理属于最终写回阶段。

## 3 矩阵到了一维内存里

行主序把一行接在另一行后面。A 的实际序列是 `1,2,3,4,5,6`，不是存储在某个
神奇的二维硬件网格里。地址公式是：

```text
A[row,k]   → A[row*K+k]
B[k,col]   → B[k*N+col]
C[row,col] → C[row*N+col]
```

例如 A[1,2] 的元素偏移是 5，值为 6。对于 float，字节偏移是 20；在 C++ 中
`A+5` 已经按元素大小移动，不要再写成 `A+20`。

这一行跨度叫 stride。紧密存储时它等于列数，有 padding 时可以更大。
即使只在计算 A 的一个小块，A 的完整行跨度也不会自动缩成 tile 宽度。
这正是很多索引错误的来源：把“我负责多宽”混成“内存一行多宽”。

## 4 存储方向与矩阵转置不是同一动作

行主序和列主序是解释内存的规则。将行主序 A 的同一块内存按转置后的形状作
列主序解释，可以得到 A 的转置视图，不一定需要真的移动全部元素。

项目中的 cuBLAS 调用利用 `(AB)^T=B^T*A^T` 调整参数，避免额外生成转置副本。
现在不必背完整 API，但要记住：行列数、stride、转置选项与指针必须一起解释。
方阵把某些错误掩盖了；将来支持矩形时更需要逐项核对。

## 5 本章到源码的距离

打开 [Kernel 1](../../../src/kernels/1_naive.cuh)，暂时忽略线程编号。
只找 `tmp`、沿 K 的循环和最后一行写回。你应该能把它们一一对应到上面的伪代码。
再注意变量 x/y 在这份实现中分别表示行/列，名字本身没有数学含义。

CPU 练习脚本的 `test_small_gemm` 会检查上述数值，`test_row_major` 检查地址。
Python 的小数计算不是设备 FP32 数值验证，这里只验证手算关系。

## 6 源码精读：把 K1 的每个变量翻译成数学

打开 [1_naive.cuh](../../../src/kernels/1_naive.cuh#L29)。以下摘录省略了原注释，
保留实际表达式；不是另写一个“长得差不多”的 kernel：

```cpp
if (x < M && y < N) {
  float tmp = 0.0;
  for (int i = 0; i < K; ++i) {
    tmp += A[x * K + i] * B[i * N + y];
  }
  C[x * N + y] = alpha * tmp + beta * C[x * N + y];
}
```

|源码对象|数学含义|保留多久|
|---|---|---|
|x、y|本线程负责的输出行、列|整个线程计算过程|
|i|当前点积位置，也就是数学里的 k|一次循环迭代|
|tmp|C[x,y] 尚未缩放的部分和|从 i=0 到 i=K-1，不能每轮清零|
|K|A 的行跨度，同时是归约长度|本次调用固定|
|N|B 和 C 的行跨度|本次调用固定|
|C 右侧的旧值|输入 C0[x,y]|最后写回前读取|

代入 x=1、y=0、M=N=2、K=3，可以把一次线程执行完整展开：

|i|A 的偏移和值|B 的偏移和值|执行后 tmp|
|---:|---|---|---:|
|0|A[3]=4|B[0]=7|28|
|1|A[4]=5|B[2]=9|73|
|2|A[5]=6|B[4]=11|139|

若 alpha=0.5、beta=3、旧 C[2]=1，写回 `C[2]=72.5`。
注意“偏移 2”和“第 1 行第 0 列”是同一个输出，不是两个结果。

### 6.1 指针为什么没有自带形状

函数参数 `float *A` 只给出地址，不会携带“这是 2×3 矩阵”的信息。
编译器不会替你判断 K 是否传对。若错误地把 A 的跨度写成 M，本例第二行就会从
A[2] 开始，读到 3、4、5；程序可能没有越界，却已经算错。这也是为什么
Sanitizer 不能替代数值对照：合法地址不等于正确地址。

`tmp` 是线程私有的局部变量；两个线程都叫 tmp，不会更新同一个累加器。
但它最终放在寄存器还是发生其他存储，要看编译结果，不能由“局部变量”一词保证。

### 6.2 beta=0 的一个真实代码差异

上面的 K1 表达式仍包含对旧 C 的读取，不能把它当成“任何情况下都不读 C”的
接口保证。K30 的 [epilogue](../../../src/kernels/30_kernel_mini_simt.cuh#L161)
则显式使用 `beta==0 ? make_float4(0,0,0,0) : ...`，在这条分支避开旧 C 读取。
本项目 audit 即使 beta=0 也初始化 C，所以它并没有专门验证“C 未初始化”场景。

练读方法：打开源码，用笔在 `x*K+i` 的每一项下标注“行基址 / 行内偏移”，
然后不看本章，自己推导 C[1,1]。你应得到 A 偏移 3/4/5、B 偏移 1/3/5。
这一步不需要 GPU，也不应拿这个微型例子直接调用有整除约束的 K30。

## 7 练习

1. 本例 C[1,0] 需要 A 和 B 的哪些一维元素偏移？
2. 如果 A 是 3×5、B 是 5×7，C 有多少个元素？A[2,4] 的 float 字节偏移是多少？
3. 为什么把最后的写回放进 k 循环，并反复应用 beta，通常不等价？

### 参考答案

1. A 的偏移 3、4、5；B 的偏移 0、2、4。沿 B 的列读取时，一维偏移间隔为 N。
2. C 为 3×7，共 21 个元素；A[2,4] 偏移 `2*5+4=14` 个 float，即 56 字节。
3. 正确计算只缩放一次旧 C。每轮重复应用 beta 会形成递推，并且部分乘积也可能
   被重复缩放。若为了分段累加而多次写回，必须重新设计 alpha/beta 协议。
