# 第 3 章 访存与数据复用

[上一章](02-把输出分给线程.md) · [目录](README.md) · [下一章](04-分块与寄存器小矩阵.md)

现在假设索引已经正确。为什么只改变线程和输出的对应关系，kernel 就可能快很多？
关键是硬件服务的不是某个线程整段循环，而是一条指令上的一组访问。

## 1 把时间固定在某个 k

考虑 N、K 足够大的行主序矩阵。第一种分工让相邻 lane 负责同一列、不同行：

```text
lane            0        1        2
输出          C[0,0]   C[1,0]   C[2,0]
某个 k 读 A   A[0,k]   A[1,k]   A[2,k]
A 元素偏移       k       K+k      2K+k
```

虽然每个线程下一轮会读 A 的下一个元素，但本轮跨 lane 的地址间隔为 K。
第二种分工让相邻 lane 负责同一行、相邻列：

```text
lane            0        1        2
输出          C[0,0]   C[0,1]   C[0,2]
某个 k 读 A   A[0,k]   A[0,k]   A[0,k]
某个 k 读 B   B[k,0]   B[k,1]   B[k,2]
```

此时 B 和 C 的跨 lane 地址更集中。A 是重复读同一位置，也有复用机会。
这就是为什么判断合并访存必须列出同一 warp、同一条指令的地址。
它不保证只有一个物理事务；访问宽度、对齐与参与 lane 都要考虑。

## 2 数据经过哪些地方

先把通路理解为逻辑层次，不当作所有指令都严格经过每一级的固定电路：

```text
完整 A/B/C：global 地址空间，访问可能命中缓存
    ↓ block 合作装载
当前 A/B 子块：shared memory
    ↓ 每线程装载 fragment
输入片段与 accumulator：registers
    ↓ FFMA
输出写回 global C
```

L1/L2 是硬件管理的缓存；shared 是程序显式管理的块内工作集。
因此“用了 shared”不等于“原来所有读都到 DRAM、现在完全不访问 DRAM”。
真正流量需看硬件指标，源码只是逻辑访问需求。

## 3 两种不同的改善

第一种改善是让一次访问更集中，减少服务分散请求的成本；第二种是少访问几次，
把已读入的数据用于多个输出。它们可以同时有用，但不是同一个问题。

拿 A[0,0] 举例，它参与整行 C 的多个列。如果每个线程独立读它，硬件缓存也许
会帮忙；如果一组线程合作把 A tile 放进 shared，就能明确建立块内复用结构。
下一章再把 shared 中的数据放到寄存器，让一次片段装载服务一个小外积。

## 4 float4 的帮助与条件

float4 将四个 float 表达成 16 字节的向量对象，可能帮助编译器生成较宽搬运。
它改变的是访问组织，不改变 FP32 数值精度，也不等于四倍性能。

假设 p 已经 16 字节对齐，p+4 个 float 仍对齐，但 p+1 未必适合 float4 访问。
此外，读取的四个元素必须全部有效。把边界附近的四个标量强行重解释成 float4，
不能让越界变安全。是否生成宽指令仍需看机器码。

## 5 Shared 的 bank 是另一层问题

用标量 FP32 简化模型：bank=`元素偏移 % 32`。
如果 32 个 lane 读 `tile[lane][0]`，行跨度 32 时全映射到 bank 0 的不同字；
行跨度改为 33，则第 lane 号线程映射到第 lane 号 bank。
同一个字被多个线程读取属于广播情形，不能误判为不同字的冲突。

这个模型用于理解 padding。遇到 LDS.128、分组服务和实际 fragment 时，要分析
实际指令，不能把标量例子直接当作所有宽访问的性能预测。
官方背景见 [Shared Memory and Memory Banks](https://docs.nvidia.com/cuda/archive/12.4.1/cuda-c-best-practices-guide/index.html#shared-memory-and-memory-banks)。

## 6 练习

1. lane l 读 `p[l]` 与读 `p[1024*l]`，哪种更集中？这能直接确定 L2 hit rate 吗？
2. float 指针 p 基地址 16 字节对齐，p+1、p+4 哪个仍满足 16 字节对齐？
3. `tile[lane][0]` 的 stride 为 32、33 时分别映射到哪些 bank？所有 lane
   都读 `tile[0][0]` 又该怎样解释？

### 参考答案

1. 前者更集中；不能直接确定缓存命中，还取决于之前访问和缓存状态。
2. p+4 增加 16 字节，仍对齐；p+1 增加 4 字节，不满足同一对齐条件。
3. 前者全部 bank 0，后者分散到 0..31；全读同一字可广播。这里讨论标量模型，
   不是完整 kernel 的所有 shared 服务成本。

练习脚本的 bank 检查只验证这个模型。对应源码先看 K1/K2 的跨 lane 地址，
再看 [K3 的合作加载](../../../src/kernels/3_kernel_shared_mem_blocking.cuh)。
