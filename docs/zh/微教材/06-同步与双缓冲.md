# 第 6 章 同步与双缓冲

[上一章](05-Warp与Shared映射.md) · [目录](README.md) · [下一章](07-验证与性能分析.md)

一个地址算对了，不代表读的时候数据已准备好；写入正确位置，也可能破坏另一个
线程尚未读完的数据。本章把同步当作数据生命周期问题，而不是看到报错就加 barrier。

## 1 单槽为什么有两种等待

设一个 block 用同一组 As/Bs 反复保存 K tile。即使所有线程的循环完全相同，
执行进度也可能不同。快线程不能假设慢线程已完成某一步。

```text
阶段一：各线程装载自己负责的数据
barrier A：确保消费者需要的 tile 已发布
阶段二：各线程读取 shared 并更新 accumulator
barrier B：确保旧读者全部退出
阶段三：覆盖 shared，装载下一 tile
```

barrier A 保护“读之前写完”，barrier B 保护“写之前读完”。这是两条不同的依赖。
如果删除 B，某个快线程可能已写入 tile1，而慢线程还在读 tile0，最终得到混合结果。
一次数值检查没失败，不代表这个竞争不存在。

## 2 双槽改变了可以并行的工作

现在准备 slot0 和 slot1。初始发布 tile0 后，本轮读 current，下一块写 future。
两个位置不同，因此它们的 shared 访问不会因覆盖同一槽而冲突。

|轮次|读取|准备写入|轮末必须成立|
|---|---|---|---|
|0|slot0 的 tile0|slot1 的 tile1|tile1 可读，tile0 的读者退出|
|1|slot1 的 tile1|slot0 的 tile2|tile2 可读，tile1 的读者退出|
|2|slot0 的 tile2|slot1 的 tile3|tile3 可读，tile2 的读者退出|
|最后一轮|当前有效 tile|不再装载越界 future|按协议完成最后一次同步|

两槽协议可以让一次轮末 barrier 同时完成发布 future 和回收 current。
但这不等于任何实现都可以随意删同步：装载是否异步、参与者是谁、每轮何时覆盖，
都必须与证明一致。

## 3 写出安全性不变量

对每个 slot，只允许遵循下面的生命周期：

```text
空闲 → 写入中 → 已发布 → 读取中 → 读者全部退出 → 可复用
```

检查代码时逐项问：

1. 第一次读取前，谁负责初始化与发布？
2. 读取结束之前，有没有线程可能复用同一 slot？
3. 最后一次迭代会不会提交不存在的 future？
4. 各参与线程是否经过匹配的 barrier 阶段？

这种问法比“代码里已经有两个 syncthreads 应该安全”可靠。barrier 数量相同，
位置与参与者不同，仍可能错误。

## 4 看懂 K30 的双槽实现

K30 V2 先装载并发布 tile0。在主循环中，源码先请求 future 的 global fragment，
然后读取当前 shared 做 compute，再将 future 写入另一个槽，最后一次
`__syncthreads()`。所有线程都同时承担搬运和计算职责，不是专职 producer/consumer。

注意三个不同概念：两个 shared slot、源码写在前面的 load、实际机器码中的重叠。
前两项可从代码看出，第三项不能猜。K30 的 SASS 把主循环 LDG 下沉到计算尾部，
因此不能因为有双缓冲就宣称“大部分访存延迟都被隐藏”。

## 5 异步复制和 warp 分工为什么更难

异步复制提交返回，不等于目的数据就绪。它需要相应的等待及可见性规则，且旧槽
的读者退出也仍需保证。原子操作或 volatile 不会自动替代这套协议。

专职 warp 分工又改变参与者、线程数和资源分配。K32 使用一个 producer 加四个
consumer，并采用匹配参与人数的 barrier；它与 K30 的全块共同搬运不是同一结构。
本书不把其分支内同步片段抽成通用模板，使用前必须读
[K32 完整协议](../19-K32-Warp角色分工与同步代价.md)。

## 6 怎样验证你画的时间线

CPU 上可以枚举或模拟事件顺序，检查是否读未就绪数据、覆盖活动读者或死锁。
本仓库的有限状态测试是：

```bash
python3 scripts/test_k32_protocol.py
```

它覆盖约定模型中的少量 tile 数，不能替代真实 GPU 检查。
GPU 还要运行数值对照、memcheck、racecheck 和 synccheck，具体范围在复现手册中。
同一 warp 内交换数据也不能仅靠“看起来同时执行”，需满足相应同步规则。

## 7 练习

1. 单槽实现只有“写后 barrier”，为何可能在下一轮出错？
2. 双槽最后一轮没有 future，能让一部分参与线程随意提前退出吗？
3. 两个实现均通过有限状态模型和 Sanitizer，是否说明性能相同？

### 参考答案

1. 快线程可能越过 compute，覆盖慢线程还在读取的 slot；缺的是消费者退出保护。
2. 不能随意退出，应保持协议要求的参与关系。可以不装载越界 future，但仍需
   经过规定同步，直到不再有跨线程依赖。正确性来自具体协议，不是固定口号。
3. 不说明。正确性只是前提，资源、指令、等待与吞吐可能不同；K32 就有这样的对照。
