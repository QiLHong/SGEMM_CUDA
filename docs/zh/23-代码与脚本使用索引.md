# 代码与脚本使用索引

这份索引写给第一次接触 CUDA 项目的人。你不需要按文件名顺序把所有脚本运行一遍。
先分清“计算代码”和“实验工具”：前者决定怎么做矩阵乘法，后者负责编译、检查、计时、采样和整理证据。
本页覆盖当前分支的 122 个受 Git 管理的代码、脚本及构建配置文件；每个文件开头都有中文导读。

当前最佳研究基线是 K30 V2；主 `sgemm` 程序的教学分发入口仍只支持编号 0–23。
因此 `./build/sgemm 30` 不是运行 K30 的方法。K31/K32 是后续对照实验，编号更大不代表更快。

## 先认识文件和术语

| 写法 | 用初学者的话解释 | 在这个项目中的例子 |
|---|---|---|
| `.cu` | CUDA 源码，需要先编译，不能直接当脚本运行 | `sgemm.cu`、`scripts/k30_audit.cu` |
| `.cuh` | 被其他源码包含的 CUDA 头文件，常放模板 kernel | `src/kernels/30_kernel_mini_simt.cuh` |
| `.sh` | Bash 脚本，按顺序调用编译器或程序 | `bash scripts/build_k30_audit.sh ...` |
| `.py` | Python 脚本，有些检查公式，有些调度 GPU 程序 | `python3 scripts/run_k30_audit.py --help` |
| binary | 编译好的可执行文件，不是源码 | 构建目录中的 `audit` 或 `sgemm` |
| kernel | GPU 上执行的计算函数 | `sgemmK30` |
| host / device | CPU 端控制 / GPU 端执行 | host 分配内存并发射 device kernel |
| CTA / block | 一组能协作、共享缓存和同步的线程 | K30 一个 block 128 个线程 |
| warp / lane | 32 线程小组 / 小组内的编号 0–31 | `warp=tid/32`，`lane=tid%32` |
| tile / fragment | 分出来的矩阵块 / 分给某个线程的一小组值 | block tile、A fragment、结果 fragment |
| accumulator | 还没算完、需要不断加上新乘积的部分和 | `acc[i*8+j] += fa[i]*fb[j]` |
| iterator | 记住当前地址、取数后能前进的游标 | `load()` 取当前片段，`advance()` 前进一个 k |
| stage | 一份可以轮流使用的缓存槽 | 双槽流水不是“两个 warp” |
| spill | 寄存器分配不下而转到 local memory 的数据 | 看 ptxas 的 spill load/store，不只看数组长度 |
| SASS / ptxas | GPU 最终指令 / 将 PTX 编译成机器码的工具 | `cuobjdump` 导出 SASS，build.log 记录资源 |
| audit | 一套实验检查，不是另一种矩阵乘法 | correctness、fair、profile 各做一件事 |

例如，K30 的一个 lane 有 16 个 A 值与 8 个 B 值，组合更新 128 个输出部分和。
`TM=TN=4` 只是组成片段的小组尺寸，不意味着每线程最终只有 16 个结果。
读代码时先问“这个下标是全矩阵坐标、块内坐标，还是寄存器编号”，许多困惑就能消除。

### 常见 CUDA 语法不用先背

| 代码写法 | 阅读时先这样理解 |
|---|---|
| `__global__` | 一个可以从主机发射到 GPU 的 kernel；不是普通 CPU 函数 |
| `__device__` | GPU 上使用的函数或声明；本项目常用它拆分加载、计算和写回 |
| `<<<grid, block, sharedBytes>>>` | 发射多少个 block、每个多少线程、每 block 额外分配多少动态 shared 字节 |
| `__shared__` | 一个 block 内共同使用的存储，其他 block 不能直接共享这份数组 |
| `threadIdx.x` / `blockIdx.x` | 当前线程在 block 内的编号 / 当前 block 在 grid 中的编号 |
| `template` / `constexpr` | 尺寸等信息在编译时确定；改模板参数需要重新编译 |
| `#pragma unroll` | 请求编译器展开循环；最终怎么排指令仍看编译产物 |
| `__restrict__` | 向编译器承诺相应指针的访问不违反别名约束，不能在实际重叠的 A/B/C 上随意使用 |
| `__launch_bounds__` | 向编译器提供线程数与资源目标，不是保证运行时始终驻留某个 block 数 |
| `CEIL_DIV` | 向上取整除法，只算需要多少块；不负责阻止尾块线程越界 |

`alpha` 和 `beta` 只是数学缩放系数，不是 CUDA 特殊语法。`beta=3` 时旧 C 要乘 3 加回来；
因此“重复计时前是否复位 C”会改变你实际重复计算的问题。

## 两条调用链

传统教学入口按数字选核；现代研究入口用独立程序公平比较。它们共用部分设备代码，但参数入口不同。

```text
教学路线
  sgemm.cu：分配矩阵、验算、计时
    → src/runner.cu：按编号选择参数和发射方式
      → src/kernels.cuh：包含对应头文件
        → src/kernels/1...23：GPU 计算

研究路线
  build_k30_audit.sh：编译出 audit
    → run_k30_audit.py：选择动作和测试组合
      → k30_audit.cu：统一输入、严格 FP32 对照、C 复位、计时
        → K10 / K30 / strict cuBLAS
    → analyze...：分析映射、编译产物或采样报告
    → summarize...：把完整证据整理为报告表格
```

`.py` 放在 `scripts/` 里不代表它只在 CPU 上做事。`run_*` 通常会调用 GPU 程序；
`analyze_*` 通常是离线分析，但有的仍需要 CUDA 工具来读二进制。每个文件导读都注明了前提。

## 读懂命令而不是盲目复制

```bash
python3 scripts/run_k30_audit.py correctness --binary <audit路径> --output <新的结果目录>
```

`correctness` 是动作名；`--binary` 后面接已编译程序；`--output` 后面接本次日志的存放位置。
`<...>` 是让你替换的说明文字，不能连尖括号原样复制。参数名称保留英文，便于对应源码。

Shell 中 `${VAR:-默认值}` 表示“外部没设置就用默认值”；`"$VAR"` 中的引号保护路径里的空格。
`COMMAND > file` 会覆盖同名文件，而 `2>&1` 把错误输出也保存进去。
带 `\` 的多行命令是一个命令；不要把解释文字接在续行反斜杠后面。
Python 的 `open('x')` 则拒绝覆盖已有文件；看到 FileExistsError 应换新目录，不要先删掉旧实验。

## 从 K30 开始的最小实验路线

以下命令在仓库根目录执行，需可用的 CUDA 12.4/SM86 环境与空闲 GPU；不要同时跑多个性能实验。
它们是你之后复现时的操作说明，本次中文注释更新没有新增性能数据。

### 先在 CPU 上检查理解

```bash
python3 scripts/check_microbook_examples.py
python3 scripts/test_audit_log_checks.py
python3 scripts/test_k32_protocol.py
python3 scripts/analyze_k30_mapping.py --output benchmark_results/study-lane-map-session1.csv
```

前几项成功会显示 unittest 的 `OK`；映射脚本会报告 exact coverage、no overlaps。
映射 CSV 只列 128×128 CTA 的 warp 0，但脚本还检查 256×128 CTA 的完整覆盖。
它证明“每个输出格子分给了谁”，不是已经在 GPU 上算对或跑快。

### 构建并跑一次小矩阵

```bash
SGEMM_STUDY_OUT=benchmark_results/study-k30-session1
bash scripts/build_k30_audit.sh "$SGEMM_STUDY_OUT"
env -u NVIDIA_TF32_OVERRIDE "$SGEMM_STUDY_OUT/audit" v2 128 3 1 0
```

`SGEMM_STUDY_OUT` 只是这次实验的路径名字，目录必须尚不存在。最后一行依次表示：
K30 V2、边长 128、beta=3、计时一次、不额外预热。它是小规模冒烟检查，不适合拿来报性能。
构建的 `build.log` 记录寄存器与 spill；`sha256.txt` 用来确认当时用的是哪份源码/二进制。

### 通过完整验算后再计时

```bash
python3 scripts/run_k30_audit.py correctness --binary "$SGEMM_STUDY_OUT/audit" \
  --output "$SGEMM_STUDY_OUT/tests" --modes k10 v2
python3 scripts/run_k30_audit.py memcheck --binary "$SGEMM_STUDY_OUT/audit" \
  --output "$SGEMM_STUDY_OUT/sanitizer" --modes v2
python3 scripts/run_k30_audit.py sync --binary "$SGEMM_STUDY_OUT/audit" \
  --output "$SGEMM_STUDY_OUT/sanitizer" --modes v2
python3 scripts/run_k30_audit.py fair --binary "$SGEMM_STUDY_OUT/audit" \
  --output "$SGEMM_STUDY_OUT/timing" --modes strict k10 v2 --rounds 3
```

这里是 2 个自写模式 × 6 尺寸 × 3 种 beta，共 36 项数值检查，绝对误差门槛仍为 0.01。
memcheck 对 V2 检查 128/256/4096；sync 的 racecheck/synccheck 只查 128/256。
工具的零错误与数值 PASS 都要看。三个动作输出的不同文件可共存于 sanitizer 目录，但不能原样重复覆盖。

正式 fair 在 4096³、alpha=0.5、beta=3 下每模式预热 10 次、计时 50 次，三轮循环移位。
每次 GEMM 前都恢复同一份 C0，复位 copy 不计入 event；这测的是该约定下的核时间，不是端到端时间。

这条入门路线只测 strict/k10/v2，先读 `timing/fair.csv` 即可。
不要直接把不完整的三模式结果交给默认要求全部 K30 变体的 `summarize_k30_audit.py`。
要生成完整收尾报告，请按[复现文档](20-项目复现与简历讲述.md)的 K32 harness 路线运行；
那里 `k30` 模式同样指 K30 V2，并有更完整的资源/证据检查。

### 学会读一行结果

`RESULT,mode,size,beta,ms,gflops,max_abs_error,PASS` 的各项如下。

| 字段 | 应怎样理解 |
|---|---|
| `ms` | 该进程内多次 GEMM 的平均毫秒数，越小越快 |
| `gflops` | 按约 `2*N^3` 次浮点操作除以时间得到的吞吐，不是带宽 |
| `max_abs_error` | 计时前候选与严格 FP32 参考之间的最大绝对差 |
| `PASS` | 本次输入/尺寸/beta 通过验算，不是任意输入的数学证明 |
| CSV 的 `round` / `position` | 第几轮与轮内第几个执行，帮助检查顺序偏差 |
| `gpu_before` / `gpu_after` | 温度/时钟快照，不能保证中间完全没波动 |

先确认同一批次 strict/K10/K30 都在，再看多轮均值和波动。
`K30/cuBLAS` 是达到参考库吞吐的比例，`K30/K10-1` 才是相对 K10 的提升；不要把两者写反。

## 历史工具先读再运行

- `kernel_9/10/11_autotuner.sh` 会改源码，且含旧参数匹配规则，不是新手的一键复现工具。
- `kernel_10_rtx3080_tuner.sh` 不原地改源码，但其历史性能分母是编号 0 的 cuBLAS，不是编号 13 strict。
- `gen_benchmark_results.sh` 只跑旧编号 0–10；`plot_benchmark_results.py` 会写图片和 README。
- `Makefile` 的 clean/profile/bench 有删除构建产物或覆盖输出的行为，先看配方。
- K18–K23 的构建/分析脚本很多使用固定 `build-...` 路径；换目录不会自动让所有下游脚本跟着变化。
- 早期 `profile_kernel_*` 按函数选第一个 launch，可能选到验算调用；现代 audit 用 NVTX `measure/` 过滤计时调用。
- 历史表中名为 `no_eligible_pct` 的列有些实际是 `issue_inst0`，表示没有发射指令；不要只看列名推断。

## 看不懂时怎么拆解

不要先背所有公式。对一个函数做四个小问题：

1. 输入在哪里：CPU、global、shared 还是寄存器？
2. 这个线程负责搬哪些数，又负责算哪些输出？这两者可能不是同一块。
3. 谁会读别人刚写的东西，在哪一道同步之后才安全？
4. 输出写到哪里，是否用了同一张线程分工表？

例如看到 `acc[i*8+j]`，先画一个 16×8 的小表，再查 `map.m(i)` 和 `map.n(j)`。
表中的第 `(5,4)` 格不是全矩阵第 `(5,4)` 格，而是本线程负责的第 6 个行坐标和第 5 个列坐标组成的结果。
这种“本地编号到全局坐标”的转换，就是理解 fragment 和 iterator 的关键。

## 注释更新与历史结果的关系

此次整理只增加中文导读、关键步骤解释和导航，不改变 kernel 算法、精度配置、误差门槛、实验参数或历史 CSV。
源码加注释后文件哈希和行号会改变，带 lineinfo 的构建产物也可能改变；
不要为了让旧哈希看起来一致而覆盖历史 `sha256` 或编译记录。
旧数据应继续按当时提交和记录解释，新实验另开目录。

纯翻译验证仍固定 `aadcd8e`，不负责验证当前所有真实算法改动。
本轮注释检查另外比较 Python AST、CUDA 非注释 token 以及脚本/构建有效行，并运行 Shell 语法与现有 CPU 检查。
