# SGEMM 项目复现与简历讲述：SIMT 与 Tensor Core

本项目基于 Simon Boehm 的开源 SGEMM 教学实现，在 RTX 3080 上研究严格 FP32

完整来龙去脉见[优化故事](06-RTX3080-K10优化故事.md)，具体指标以各版本 CSV 为准。
本页解决三个问题：如何理解成果、如何从干净环境复现、如何准确地用于求职。
面试练习另见[模拟面试 QA](21-SGEMM模拟面试QA.md)。

## 1 项目要证明什么

计算是行主序 FP32 `C = alpha*A*B + beta*C`。目标不是改变算法复杂度，而是让
有限的线程、寄存器和 shared memory 更有效地复用数据、发射 FFMA。
SGEMM 常用工作量按 `2*M*N*K` 计，每次 FMA 算两个浮点操作；不另计 epilogue。
当 N=4096、耗时约 6.607 ms 时，得到约 20.8 TFLOPS。

不要把两个“百分比”混在一起：

- `K30 / cuBLAS` 是达到参考库吞吐的比例，约 96.33%。
- `K30 / K10 - 1` 是相对自写稳定基线的提升，约 5.85%。
- 96.33% 不是 GPU 理论峰值利用率，也不表示对所有 GEMM 形状都达到该比例。

初版 benchmark、原作者 A6000 数据和本机固定 C0 的公平 benchmark 属于不同口径。
只在同一批数据内比较，不能拿某天较高 K30 与另一天较低 cuBLAS 相除。

## 2 三个最值得讲清楚的转折

### 先修测量再讨论优化

原 benchmark 的 beta=3 如果持续覆盖 C，会变成递推：
`C(t+1)=alpha*AB+3*C(t)`，不再是重复计算同一输入，数值会不断放大。
公平入口每次先将 C 恢复到 C0，再启动 kernel；恢复 copy 在 event 之外。
这定义的是固定输入下的 kernel 时间，不是包含恢复 copy 的端到端时间。
恢复过程也会影响缓存，因此所有模式必须采用同样方法。

cuBLAS 使用 `CUBLAS_PEDANTIC_MATH`、`CUBLAS_COMPUTE_32F_PEDANTIC` 和
`CUBLAS_GEMM_DEFAULT`；运行脚本清除 `NVIDIA_TF32_OVERRIDE`，并通过 SASS/Nsight
检查实际路径。不能仅凭数据类型叫 float 就断定乘法精度是严格 FP32。

### 零 bank conflict 不代表 shared 已无优化空间

K10 的 shared-load conflict 可以为零，但同样数量的 LDS 指令仍可能需要不同
数量的基础 wavefront 才能服务整个 warp。K30 重构了每个 lane 负责哪些输出，
使主循环 LDS 服务量由约 335.54 M waves 降到 201.33 M，减少约 40%。
这和“消除了 40% bank conflict”不是一回事。

单阶段 K30 V1 已有这项变化，却比 K10 慢。真正的成功版本 V2 还采用两个 shared
slot 和一次发布/回收 barrier：当前计算与下一 tile 写入不覆盖同一槽，再通过
同步确保下一槽可读、当前槽读者全部退出。不能把组合收益全部归功于 layout。

### 不相信源码看起来像流水

K30 源码把 future load 写在 compute 前，SASS 却把主循环 LDG 下沉到 2,046 条
FFMA 之后。因此项目没有证明大范围 global-load/compute overlap 是主要增益。
K32 尝试专职搬运 warp，确实降低 long-scoreboard，最终吞吐仍与 K30 持平。
减少一次 barrier 又改变寄存器分配，使驻留 CTA 从两个降到一个。优化对象必须
是最终机器码及执行效果，而不只是源码写法。

## 3 最小可讲明白的 K30 数据流

```text
CTA 128×128 输出，128 threads，4 warps，BK=16
  → 每 warp 64×64 输出
  → 4×8 lane lattice，每 lane 16×8 输出
  → Shared A/B iterator 每个 k 取 A16 和 B8
  → 128 个 accumulator 执行 16 轮更新
  → 两个 shared slot 轮换并同步
  → epilogue 执行 alpha*acc + beta*C
```

两个 slot 占用户 shared 33,280 B，编译器分配 235 registers/thread，无 spill。
128 个 accumulator 只占其中一部分，其余还涉及 fragment、全局搬运临时量、地址
和控制状态，不能直接用源码数组长度精确解释全部物理寄存器。

以 warp 0 的 lane 0 为例：负责 M 坐标 `0..3,16..19,32..35,48..51`，
N 坐标 `0..3,32..35` 的笛卡尔积，共 128 个元素。
lane 1 将这些 M 坐标整体加 4，lane 2 将 lane 0 的 N 坐标整体加 4。
其余 warp 加上对应的 64 行或 64 列偏移。完整公式和实现见
[K30 报告](17-K30-Mini-SIMT微内核.md)及
[FragmentIterator](../../src/kernels/30_kernel_mini_simt.cuh)。

## 4 从干净目录复现

### 环境和版本检查

参考环境为 RTX 3080 10 GB、SM86、CUDA Toolkit 12.4、Nsight Compute 2024.1。
GPU 型号、编译器和库版本改变可能改变机器码与 cuBLAS 选核；不同机器不保证复现
相同 GFLOPS。`nvidia-smi` 上的 CUDA Version 不等于实际 nvcc 版本。

```bash
git clone --branch zh-cn-learning https://github.com/QiLHong/SGEMM_CUDA.git
cd SGEMM_CUDA
git status --short
git rev-parse HEAD
nvidia-smi
nvcc --version
ncu --version
compute-sanitizer --version
command -v cuobjdump nvdisasm
```

将本次使用的完整 commit、GPU/驱动/工具版本记入自己的实验记录。分支会继续演进，
引用论文或简历附件时应固定 commit。确保 GPU 无其他计算任务；不要并行跑 profiler
与 benchmark，也不要为得到分数擅自改变服务器功耗/频率配置。

### 无 GPU 也能做的检查

```bash
python3 scripts/verify_zh_translation.py
python3 scripts/test_audit_log_checks.py
python3 scripts/test_k32_protocol.py
```

翻译验证固定提交 `aadcd8e`，验证的是翻译阶段，不是把后续算法修改判为翻译失败。
CPU 协议模型只检查约定事件及有限 tile 数，不替代 GPU Sanitizer。

### 一次构建获得 K10 和 K30 的公平对照

最新 `k32_audit` 同时包含未修改的 K10/K30 和三个 K32 研究版本，最适合复现收尾结果。
它不会改变主 `sgemm` dispatcher。以下目录必须不存在；重复执行时更换目录名，
不要删除或覆盖旧结果。

```bash
OUT=benchmark_results/reproduce-k32-session1
bash scripts/build_k32_audit.sh "$OUT"
python3 scripts/analyze_k32_binary.py "$OUT"
python3 scripts/run_k32_audit.py resources --directory "$OUT"
env -u NVIDIA_TF32_OVERRIDE "$OUT/audit" k30 128 3 1 0
```

构建固定 `-O3 -DNDEBUG -std=c++17 -arch=sm_86 -lineinfo` 并记录 ptxas 资源。
直接运行的参数顺序为 `mode size beta repeat warmup`。
`k30` 对应 K30 V2，不是四个 K30 变体一起混测。冒烟检查通过不等于完整验证。

### 完整正确性和工具验证

```bash
python3 scripts/run_k32_audit.py correctness --directory "$OUT"
python3 scripts/run_k32_audit.py memcheck --directory "$OUT"
python3 scripts/run_k32_audit.py sync --directory "$OUT"
```

正确性矩阵是五个自写模式 × 六尺寸 × beta=0/1/3，共 90 项，逐元素有限值且
绝对误差不超过 0.01。Sanitizer 为四个研究模式 K30/serial/overlap/single：
memcheck 128/256/4096，racecheck/synccheck 128/256，共 28 项。
不能写成“所有尺寸都跑了全部 Sanitizer”。严格 cuBLAS 是参考，不是额外一个
独立数值 oracle；当前检查也没有证明任意数据分布的稳定性。

### 公平性能测量

```bash
python3 scripts/run_k32_audit.py fair --directory "$OUT" --rounds 6
```

默认比较 strict、k10、k30、serial、overlap、single，六轮循环移位覆盖各执行位置。
先热身，正式各模式 warmup=10、repeat=50，n=4096、alpha=0.5、beta=3，
固定 seed=20261013。每次恢复 C0，CUDA event 只包住 kernel，记录温度与频率快照。
轮内平均值保存于 `timing/fair.csv`；不要只挑最高一轮。

### 硬件指标与 SASS

```bash
python3 scripts/run_k32_audit.py profile --directory "$OUT"
python3 scripts/run_k32_audit.py source --directory "$OUT"
python3 scripts/run_k32_audit.py profile --directory "$OUT" --policies steady \
  --modes strict k30 overlap single
REPORT=docs/results/reproduce-k32-session1
python3 scripts/summarize_k32_audit.py "$OUT" --output "$REPORT" --rounds 6 \
  --steady-modes strict k30 overlap single
python3 scripts/analyze_cutlass_reference_source.py "$OUT/source" \
  --modes strict k10 k30 serial overlap single --skip-mapping --output "$REPORT/source"
python3 scripts/analyze_k32_payload_liveness.py "$OUT" --output "$REPORT/static-analysis"
```

profiling 比计时慢很多。cold 与 steady 的 replay/cache/clock policy 不同，分开
比较，不能把 profiler duration 放进公平性能表。最后一个脚本是离线静态追踪，
不是新的硬件性能结果；编译器改变指令模式时它会拒绝分析，应检查差异而非删断言。
汇总要求完整验证集与指定 profile 文件，不完整时应保留失败状态，不能补造 PASS。

## 5 读懂输出并处理复现差异

|文件|解决的问题|
|---|---|
|`performance.csv` 与 `fair.csv`|均值、波动、每轮执行顺序是否支持提升|
|`correctness.csv`|哪些 mode/size/beta 已验证、最大误差是多少|
|`ptxas.txt` 与 `resources.csv`|编译寄存器、stack、spill、shared 模型|
|`runtime-resources.csv`|实际属性和理论可驻留 CTA 数，不是运行时保证|
|`nsight.csv`|issue、FP32、stall、cache、local memory 等整核指标|
|`source/*.csv`|动态指令、具体 PC stall 与 shared 访问|
|`sha256.csv`|测量时二进制与源码对应关系|
|`sanitizer.csv`|工具范围、结果摘要与原始日志哈希|

仓库保存 CSV、编译日志及复现脚本；完整 `.ncu-rep`、可执行文件和大日志保留在
本地 `benchmark_results`，不随 Git 上传。仅凭日志哈希无法还原日志，远端读者可
通过上述命令重新生成。历史环境文件记录的 HEAD 是当时实验前提交，结合源码
哈希判断测量对象，不要误以为那个旧提交已包含尚未提交的研究代码。

常见情况：

- NCU 无计数器权限：联系服务器管理员按既有策略开放；性能计时可以单独完成，
  指标应标记未采集，不用其他机器的数据填补。
- 输出目录已经存在：选择新目录，不覆盖上一轮；失败日志也是实验记录。
- 分数不同：先检查温度/频率、共享 GPU 负载、CUDA/cuBLAS 版本、编译参数及
  C 复位策略，再看同轮比例；没有稳定优势就不能宣布重现提升。
- Sanitizer 或数值检查失败：停止排名，先检查尺寸契约、对齐与同步；不要放宽误差。
- 仅有 CPU：可以检查源码、CSV 和协议模型，不能声称完成 CUDA 编译或硬件验证。

## 6 简历怎样写才经得起追问

下面是成果表述模板，第一人称经历和个人贡献须按实际参与情况改写，不直接把
AI 辅助完成的全部工作写成独立原创。

> 基于开源 SGEMM 教学项目，在 RTX 3080 上研究严格 FP32 SIMT 微内核；通过
> fragment ownership 与双缓冲同步协议协同重构，4096³ 七轮交错测量达到
> 20.8 TFLOPS、同口径 cuBLAS 的 96.3%，较已调优 K10 提升 5.85%，独立复测确认。

可配第二条：

> 建立固定输入与 C 复位的 benchmark、六尺寸三 beta 数值验证及 Compute Sanitizer
> 检查；结合 Nsight Compute、SASS 和 ptxas 统计定位 shared 服务量、同步与资源
> 驻留约束，保留失败实验及可复现 CSV。

不要写“从零独创所有 kernel”“超过 cuBLAS”“通用 GEMM 提升 5.85%”“解决了
cuBLAS 剩余差距”或“96.3% 理论峰值”。不是生产替代库，没有测试任意矩形、batch、

### 两分钟讲述模板

“项目起点是一个开源 CUDA SGEMM 教程。我关心的不是照搬 tile 参数，而是如何
在自己的 RTX 3080 上证明优化有效。先统一严格 FP32 cuBLAS、输入、beta 与 C 复位，
发现 K10 稳定在约 91%。随后缓存重排、简单异步和 fragment 预取都没有稳定收益。

转折来自逐 PC 的 shared 访问分析：零 bank conflict 不等于相同服务成本。我用
独立 K30 skeleton 重构 lane 的输出 ownership，再配合双 slot 和单 barrier 协议，
把 shared-load wavefront 降低约 40%，七轮达到 20.8 TFLOPS、96.3% cuBLAS。
单阶段对照仍然更慢，所以我把结论限定为组织方式的组合有效。

后续精修和 warp 分工没有产生可靠新最佳，反而揭示了编译调度与寄存器子分区
阈值的影响。最终保留最稳版本和全部失败证据。目前暂停继续优化，成果是一个
可解释、可复现的微内核研究流程，而不是宣称完成了生产级 cuBLAS 替代。”

### 准备面试的最低要求

能手画 lane 0/1 的输出坐标、解释一轮 slot 发布与回收、现场计算 GFLOPS，
并从仓库找出一次成功与一次失败的 CSV。先按复现命令亲自跑过，再用自己的话

## 7 RTX 4090 D Tensor Core：单独复现、单独讲述

### 先给这段工作一个准确名字

建议称为 **Windows RTX 4090 D Tensor Core GEMM 复现、分块优化与精度审计**。
基于 QiLHong / vitamin-cuda 提交 `520f97093a2abc239977be83d244b327d0e2e2ef` 的实现，
先分离 device kernel 与 PyTorch 绑定，建立原生 CUDA 入口，再派生 BK32 与 BN64 实验。
原作者代码、派生改动和测试工程的贡献要分别说明；不是所有 kernel 都由本项目从零编写。

这条路线没有改变第 1–6 节的历史结论。下面的 57.998 TFLOPS 不能和 RTX 3080 的
20.8 TFLOPS 相除，写成相同精度的算法提升；它们来自不同 GPU、精度和工作负载协议。

| 项目 | RTX 3080 历史路线 | RTX 4090 D BN64 路线 |
|---|---|---|
| 计算语义 | `C=0.5*AB+3*C0` 的指定公平实验 | `C=AB`，alpha=1、beta=0 |
| 主计算 | strict FP32 SIMT / FFMA | 显式 TF32 输入，FP32 累加和输出 |
| 库对照 | PEDANTIC FP32 cuBLAS | `CUBLAS_COMPUTE_32F_FAST_TF32` |
| 代表环境 | SM86 / Linux 路线 | Windows、sm_89、CUDA 12.4.131、MSVC 19.37 |
| 主机入口 | 历史 `k30_audit` / `k32_audit` | 独立 `experiments/tensorcore-bn64` |
| 精度结论 | 指定验证集通过原严格阈值 | 原始 FP32 的绝对 0.01 / SIMT allclose 失败 |
| Sanitizer 范围 | 以上文记录的已完成范围为准 | 本轮未执行，仍为未验证 |

### 当前能展示的结果与反例

BN64 独立确认的同批结果如下。TFLOPS 从七个轮均值延迟的中位数换算；提升百分比
是七个同轮延迟比的中位数，并不是表中两个 TFLOPS 直接相除。

| N | 作者原版 TFLOPS | BN64 TFLOPS | TF32 cuBLAS TFLOPS | BN64 对原版 / 对库配对提升 |
|---:|---:|---:|---:|---|
| 1024 | 31.363 | 32.599 | 35.646 | +4.11% / −8.45% |
| 2048 | 48.503 | 57.998 | 51.973 | +19.56% / +11.57% |
| 4096 | 71.504 | 71.156 | 69.222 | −0.43% / +2.79% |

2048 对原版与库均七轮胜出；4096 对原版只赢两轮，不能写成所有尺寸都得到优化。
原始来源为[确认统计](../../results/windows/20261021-tensorcore-bn64/confirm-analysis02/summary.csv)
和[逐轮配对](../../results/windows/20261021-tensorcore-bn64/confirm-analysis02/paired-rounds.csv)。

最值得讲的转折是：BK16→BK32 减少每 CTA 的循环与 barrier 次数，却让 shared 从
32 KiB 增到 64 KiB、寄存器从 127 增到 170，理论 CTA/SM 从 2 降到 1，大尺寸回退。
再将 BN128→BN64 后，shared 为 48 KiB、寄存器为 102、理论 CTA/SM 恢复为 2；
但 CTA 数翻倍、A 重复请求增加，所以 2048 的收益不能外推到 4096。
这是组织方式之间的权衡，不能描述为只改 occupancy 就证明全部因果关系。

### 可以怎样写成果，哪些限定词不能省

以下模板仍需按自己的实际参与程度改写，不把 AI 辅助或上游实现包装成个人独创：

> 基于 vitamin-cuda 在 Windows RTX 4090 D 上复现 Tensor Core GEMM，并对 BK/BN
> 分块进行独立对照。统一显式 TF32 输入、FP32 累加和输出、C0 恢复及七轮交替计时；
> BN64 在 2048 方阵达到 57.998 TFLOPS，同批逐轮配对中位数较作者基线提升 19.56%，
> 较 TF32 cuBLAS 提升 11.57%。保留 4096 未继续改善的反例及数值误差、NCU/SASS 证据。

被追问时要立即补充：转换、C0 恢复和 CPU 检查均在 event 外；结果是 kernel 时间，
不是完整应用端到端时间。原始 FP32 的误差标准仍失败，不能说“保持严格 FP32 精度超过
cuBLAS”。Sanitizer 未执行，不能借用 RTX 3080 阶段的 PASS 给新 kernel 背书。

同日固定输入、三个方阵、未锁频 WDDM 环境也属于结论边界。不要写成通用 GEMM 库，
