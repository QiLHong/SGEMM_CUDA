# RTX 3080 FP32 基线与 Kernel 10 瓶颈审计

日期：2026-10-10（Asia/Shanghai）

环境：NVIDIA GeForce RTX 3080 10 GB（SM86）、驱动 550.127.05、CUDA 12.4、
Nsight Compute 2024.1。目标为 4096³ SGEMM，`alpha=0.5`、`beta=3`。

## 1. 本轮修复了什么

- 翻译验证固定比较上游 `5a7dcc5` 与纯翻译提交 `aadcd8e` 的 Git blob；不再用当前
  工作树误判后续真实性能改动。
- 保留 kernel 0 的历史入口，另增 kernel 13（pedantic FP32 cuBLAS）与 kernel 14
  （显式 FAST_TF32），不再把不同精度写进同一百分比。
- 新增固定 `SGEMM_SEED` 与 `SGEMM_RESET_C_EACH_REPEAT=1`。公平入口每次 event
  开始前恢复同一份 C，D2D copy 不计时；历史连续 `beta*C` 入口仍可复核旧数据。
  复位会统一改变各入口的缓存前置状态，因此所有被比较入口都执行同一复位策略；
  该 copy 的耗时和带宽不计入 GEMM 数字。
- 自写 kernel 改为对严格 FP32 cuBLAS 校验，原绝对误差 0.01 与 NaN 检查不变。
- K10 增加尺寸整除、float4 与线程映射的编译期/运行时约束，拒绝已知会越界或失去
  对齐的形状，而不是静默执行。
- 检查 cuBLAS/CUDA 返回值，修复演示 target 的 CMake 架构设置、helper 名称不一致和
  `bank_calc.py` 的多余参数错误。
- 调优脚本要求显式传入 `MIN_BLOCKS`，固定 seed、复位 C，并拒绝覆盖同名结果。

历史 CSV 没有被覆盖。04 文档仍记录旧 benchmark 口径，本文件记录新的公平口径。

## 2. cuBLAS 计算模式到底是什么

四个入口如下：

| 模式 | 入口 | Compute Type | Math Mode | Algorithm |
|---|---:|---|---|---|
| 历史 cuBLAS | 0 | `CUBLAS_COMPUTE_32F` | `CUBLAS_DEFAULT_MATH` | `CUBLAS_GEMM_DEFAULT_TENSOR_OP` |
| 严格 FP32 | 13 | `CUBLAS_COMPUTE_32F_PEDANTIC` | `CUBLAS_PEDANTIC_MATH` | `CUBLAS_GEMM_DEFAULT` |
| 显式 TF32 | 14 | `CUBLAS_COMPUTE_32F_FAST_TF32` | `CUBLAS_TF32_TENSOR_OP_MATH` | `CUBLAS_GEMM_DEFAULT_TENSOR_OP` |
| 自写 K10 | 10 | 普通 FP32 CUDA Core | 不适用 | 不适用 |

Nsight Compute 给出的实际 kernel 路径：

- 历史入口与严格 FP32 都选择
  `cutlass_80_simt_sgemm_256x128_8x4_nn_align1`；Tensor pipe 为 0%，FMA pipe
  约 78.6%。两者在固定输入上逐元素 bit-equal。
- 显式 TF32 选择
  `cutlass_80_tensorop_s1688gemm_128x256_16x3_nn_align4`；Tensor FP pipe
  活跃 48.71%。它相对严格 FP32 的最大绝对误差为 0.373077，16,777,216 个元素中
  14,850,391 个超过原 0.01 阈值。
- 设置 `NVIDIA_TF32_OVERRIDE=0` 后，显式 TF32 入口回退到约 21.768 TFLOPS，固定
  输入与严格 FP32 的最大差值为 0。未设置该变量时才使用上述 Tensor Core 路径。

所以，当前 kernel 0 虽然传入名为 `DEFAULT_TENSOR_OP` 的 algorithm，但在这台机器和
这些参数下实际是 SIMT FP32，不是 TF32。algorithm 名称不能代替指令/管线验证。

## 3. 公平长测结果

固定 seed 20261010、每次恢复 C、预热 10 次、每轮重复 50 次；三轮轮换执行顺序：

| 模式 | 三轮 GFLOPS 范围 | 平均 GFLOPS | 数值口径 |
|---|---:|---:|---|
| 历史参数 cuBLAS | 21,649.6–21,783.5 | 21,696.8 | 与严格 FP32 bit-equal（该输入） |
| 严格 FP32 cuBLAS | 21,617.4–21,784.9 | 21,704.9 | 参考 |
| **K10** | **19,657.9–19,769.6** | **19,696.5** | 六尺寸、beta 0/1/3 均 PASS |
| 显式 TF32 | 29,577.7–29,969.6 | 29,771.3 | 不满足原 FP32 阈值 |

K10 对同轮严格 FP32 的三个比例为 90.75%、90.56%、90.94%，平均 **90.75%**。
因此“约 90%”不是把不同轮次或不同精度交叉相除得到的。

## 4. K10 的实测瓶颈

下列 Nsight 数据来自一次单 kernel 完整采集。Profiler 会重放 kernel，8.00 ms 不能
替代上面的正常 benchmark；它只用于同次采集中的资源与比例分析。

| 指标 | K10 | 严格 FP32 cuBLAS |
|---|---:|---:|
| Registers/thread | 184 | 202 |
| Static shared/block | 16,640 B | 0 B（该 cuBLAS kernel 报告值） |
| Local load/store | 0 / 0 | 未见 spill |
| Achieved occupancy | 16.58% | 16.66% |
| Compute throughput | 74.65% | 82.1% |
| FMA pipe active | 73.64% | 78.59% |
| Issue slots busy | 79.14% | 87.33% |
| DRAM throughput | 17.41% | 10.50% |
| DRAM read traffic | 963.72 MB | 514.21 MB |
| L2 hit rate | 78.01% | 87.77% |
| Executed warp instructions | 2.336B | 2.402B |

结论是 **compute / instruction-issue bound 为主，片上数据供给与延迟为辅，不是 DRAM
带宽打满**。K10 的 compute 利用率明显高于 DRAM 利用率；FP32 roofline 达到设备峰值
约 69%。但它比 cuBLAS 少约 8.2 个百分点的 issue-slot 利用率、少约 5 个百分点的
FMA pipe 利用率，同时产生约 1.87 倍 DRAM read traffic，L2 命中率也低约 10 个百分点。

K10 scheduler 每周期有 eligible warp 的比例为 79.08%，无 eligible warp 为 20.92%。
每条已发射指令对应的主要 warp 状态为：dispatch stall 0.32、barrier 0.14、wait 0.11、
long scoreboard 0.10、math-pipe throttle 0.06。由此可以回答：

1. **184 registers/thread 合理。** `MIN_BLOCKS=0` 使用 168 registers、理论 occupancy
   25%，但 profiler duration 从 8.00 增至 8.26 ms，执行指令从 2.336B 增至 2.352B，
   dispatch/barrier/long-scoreboard stall 都更高。更高 occupancy 没有换来更高吞吐。
2. **两次 `__syncthreads()` 有成本，但不是首要瓶颈。** barrier stall 为 0.14，低于
   dispatch stall；简单删除或增加同步都没有正确性依据。
3. **global load 与计算没有流水重叠。** 当前循环是 load → barrier → compute →
   barrier，long-scoreboard 与 20.92% no-eligible 说明仍有可隐藏延迟；但 DRAM 只有
   17.41%，所以不能把全部差距归因于显存带宽。
4. **依赖/发射仍有空间。** SASS 静态主路径含 2,176 条 FFMA、2 条 `BAR.SYNC`、40 条
   `LDG.E.128`、96 条 `LDS.128`、32 条 `STG.E.128`，无 HMMA，也无 local spill。
   多累加器已经提供并行链，不是单一 FFMA 链完全串行；实测更突出的是 dispatch 和
   数据就绪造成的 issue 空洞。
5. **shared-memory 写入仍有冲突。** `AS_PAD=4` 已把冲突从 50,331,648 降到
   16,777,216，但仍有约 2.4-way shared-store 行为。Nsight 的 19.88% “估算加速”是
   规则提示，不是可直接兑现的性能预测；此前其他 padding 实测没有稳定胜过 4。

## 5. Launch Bounds 必须逐 tile 看

本轮对三类 tile 分别测试 `MIN_BLOCKS=0/1/2`，而不是让所有 128/256 线程配置共享
一个结论。每项都通过固定输入正确性校验：

| Tile | MIN_BLOCKS 0 / 1 / 2 GFLOPS | Registers 0 / 1 / 2 | 结论 |
|---|---:|---:|---|
| 当前 baseline，128 threads | 19,307.6 / 19,812.3 / 19,726.2 | 168 / 184 / 184 | 1/2 最优且 SASS 相同 |
| `sub8x4n2`，128 threads | 16,855.3 / 19,603.7 / 19,579.2 | 182 / 192 / 192 | 对 launch bound 非常敏感 |
| `threads256` | 18,061.1 / 18,026.8 / 18,103.6 | 108 / 118 / 118 | 256-thread tile 仍落后 |

每个 tile 的 1 与 2 版本 SASS hash 完全相同，资源也相同，所以它们之间的小差异属于
噪声。`minBlocks` 是 ptxas 资源目标，不是运行时保证。默认保留 2，因为它与已发布的
RTX 3080 配置一致；不能把这个选择推广到其他 tile/GPU。

## 6. 为什么 K11/K12 双缓冲反而慢

公平三轮均值：K11 为 16,977.1 GFLOPS，K12 为 15,702.7 GFLOPS，分别只有 K10 的
86.19% 和 79.72%。这次有实际 Nsight 证据，不只是代码猜测：

| 指标 | K10 | K11 | K12 |
|---|---:|---:|---:|
| Registers/thread | 184 | 170 | 210 |
| Static shared/block | 16.64 KB | 49.15 KB | 32.78 KB |
| FMA pipe active | 73.64% | 58.69% | 55.41% |
| Issue slots busy | 79.14% | 65.92% | 62.82% |
| No eligible | 20.92% | 34.05% | 37.19% |
| Barrier stall | 0.14 | 0.52 | 0.09 |
| Shared bank conflicts | 16.78M | 25.17M | 217.25M |
| DRAM read traffic | 0.964 GB | 0.692 GB | 1.45 GB |

K11 虽减少 DRAM traffic，却使用 256 threads、49 KB shared，并用半 block 分工和多次
全 block barrier；barrier stall 升到 0.52，FMA/issue 利用率显著下降。K12 的 A
转置被拆成多个 4-byte `cuda::memcpy_async`，又引入两份 C++ barrier 和双份 shared；
结果是 210 registers、极高 shared conflicts 和 1.45 GB DRAM read。异步 API 的提交
开销和等待没有被有效计算覆盖。当前双缓冲实现因此没有形成有收益的软件流水。

## 7. 失败或不采用的方案

- `--use_fast_math`、额外向量化、`maxrregcount`、cache modifier、shared carveout 和
  grid 交换均未稳定改善。
- `MIN_BLOCKS=3` 回退到约 17.4 TFLOPS；4 导致 816 B stack spill，只剩约
  0.735 TFLOPS。
- 256-thread tile、128×256/256×128 大 tile 出现资源压力或 spill，明显回退。
- K11/K12 的现成 double buffering 已由 Nsight 证明得不偿失，因此没有未经独立证明
  就重写 K10 数学主体。
- 显式 TF32 很快，但误差不满足原 FP32 门槛，不能计作 K10 的同精度优化。

## 8. 最值得继续投入的方向

优先级最高的不是继续盲搜 tile，也不是强行提高 occupancy，而是重做 **global →
shared staging 与指令调度**：目标是接近 cuBLAS 的 L2/DRAM 复用、消除剩余 shared
store conflicts，并让下一 K tile 的向量加载与当前 FFMA 真正重叠。可尝试 lane-swizzle
的 A 布局、合并而非四次标量转置的 `cp.async` 路径、较轻量的 producer/consumer
调度；每一步都必须分别观察 DRAM bytes、bank conflicts、no-eligible、issue slots 和
FMA utilization。只有这些指标同时改善，software pipeline 才值得保留。

## 9. 复现命令

```bash
cmake -S . -B build-audit -G "Unix Makefiles" \
  -DCMAKE_BUILD_TYPE=Release -DCMAKE_CUDA_FLAGS_RELEASE="-O3 -DNDEBUG"
cmake --build build-audit --target sgemm --parallel 2

# 三轮公平精度/性能对照，输出使用新时间戳，拒绝与历史 CSV 混淆。
BUILD_DIR="$PWD/build-audit" DEVICE=0 ./scripts/rtx3080_fp32_audit.sh

# beta=0/1/3 × 六尺寸，原阈值不变。
BUILD_DIR="$PWD/build-audit" DEVICE=0 ./scripts/kernel_10_correctness_matrix.sh

# 旧口径仍可运行，但必须明确它连续更新 C。
DEVICE=0 SGEMM_BENCH_SIZE=4096 SGEMM_WARMUP=10 SGEMM_REPEAT=50 \
  ./build-audit/sgemm 10

# K10 完整 Nsight；profiler 输出不能当正常 benchmark 时间。
RUN_TAG="$(date +%Y%m%d-%H%M%S)"
DEVICE=0 SGEMM_BENCH_SIZE=4096 SGEMM_REPEAT=1 SGEMM_SEED=20261010 \
SGEMM_RESET_C_EACH_REPEAT=1 ncu --set full \
  --kernel-name regex:sgemmWarptiling --launch-count 1 \
  --export "benchmark_results/rtx3080-k10-full-${RUN_TAG}" \
  ./build-audit/sgemm 10

# SASS/PTX 与资源。
cuobjdump --dump-resource-usage build-audit/sgemm
cuobjdump -sass build-audit/sgemm
cuobjdump -ptx build-audit/sgemm
```
